## 发现明细

### F1（major, FACT）coverage 现有 fail-closed 上限与计划规模硬冲突，计划通篇未提

- 证据：`github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/coverage.py#L24-L26`（`MAX_COVERAGE_CHECKS = 50_000_000`、`MAX_COVERAGE_ENDPOINTS = 10_000`）；`github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/coverage.py#L83-L98`（两个上限在 `scan_coverage` 内强制 fail-closed）；计划 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L302-L315`。
- 推理：16,988 endpoints > 10,000 上限；即便 Task 3 的 600s/60s smoke 也是 16,988×11×280 = 52,323,040 > 50M checks；24h 全量 4.11e10 更超出三个数量级。计划只说"新增 `scan_constellation_coverage()`"，但 (a) 若实现者让 population 模式复用 `scan_coverage` 的校验即立刻 fail-loud 失败；(b) 若新路径不设等价界限，又违背本仓库 fail-closed 惯例且无替代的拒绝无界工作量合同。这是计划级遗漏，会在 Task 3 smoke 首次执行时爆雷。
- 最小修改：在 Task 3 明文写出新路径的资源合同——`scan_coverage` 的三条上限保留不变；`scan_constellation_coverage` 用 `--max-working-mib` 推导分块大小并以"端点数 × 卫星数 × 采样数须可由分块覆盖"为唯一规模前提，同时声明 population 模式不经由 `MAX_COVERAGE_CHECKS`（或显式给出替代上限值）。

### F2（major, FACT）Task 6 写集遗漏 `receipt.py`，nested 编译实际消费第二条 RNG 流与 receipt 硬编码合同冲突

- 证据：计划 Task 6 文件清单 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L446-L451`（无 receipt.py）；`github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/receipt.py#L312-L315`（`expected_rng = stream_mapping(seed, ["demand"])`，不等即报错）；现有编译入口 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/trace.py#L575`；manifest 只写 demand 流 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/trace.py#L736`。
- 推理：nested 模式确定性消费 `nested_filter` 流（计划 L463-473）。若实现者保持 manifest `rng_streams` 不变，receipt 校验能过，但经 receipt 核验的 manifest 声明的随机性来源不完整（少报一条实际被消费的流）——正是 manifest 该字段存在的意义；若实现者把 `nested_filter` 加进 manifest，receipt L312-315 立即判 mismatch，Task 8 要求的"receipt verification"smoke 必然失败（计划 L711）。两条路都走不通，说明计划漏了 receipt.py 的配套改动。
- 最小修改：Task 6 文件清单加入 `CODE/leo_sim/receipt.py`；nested 模式下 manifest `rng_streams` 值扩展为 `{"demand": spawn[0], "nested_filter": spawn[1]}`（顶层 key set 不变），receipt 端按 `nested_master_offered_mbps is not None` 复现同一分支，非 nested 路径字节不变。

### F3（major, FACT）nested_master_offered_mbps 未限制 demand 模式，csv/mlab 下合同欠定义

- 证据：计划校验合同 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L168-L171`（仅查 master ≥ offered）；companion 写出条件 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L453`；csv 分支无任何候选生成 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/trace.py#L470-L554`。
- 推理：`mode: csv`（及 mlab）下不存在"在 master 负载生成候选再过滤"的路径；只要 `nested_master_offered_mbps` 非空就写 `nested-family.json` 的规则在 csv 下要么产生虚假 family 声明，要么迫使实现者即兴解释。与本仓库 fail-closed 惯例（AGENTS 硬事实 4）相悖。
- 最小修改：Task 1 校验合同加一条：`nested_master_offered_mbps is not None` 要求 `mode == "population_gravity"`（本工作包范围），其他模式直接 ConfigError。

### F4（major, FACT）决策合同中四个 fraction 阈值未定义分母，access/route 门可被歧义误判

- 证据：计划 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L557-L563`（`max_rejected_fraction` / `max_access_overflow_fraction` / `max_uplink_overflow_fraction` / `max_no_route_fraction` 均无分母）。
- 推理：以 `max_no_route_fraction: 0.001` 为例，"of offered" 与 "of admitted" 在 access 受限场景下可差两个数量级——若 access 只放行 1% 的包，按 offered 算的 NO_ROUTE 比例可以极低，按 admitted 算却可能全军覆没，同一运行可被判成 ROUTE_LIMITED 或 route_clean 两种结论。access/route 门是整个分层判据的承重墙（L4 只在 L3 clean 时才评估），分母歧义直接动摇"access failure 永不被误标为 ISL congestion"的核心承诺。
- 最小修改：在 contract v1 中逐字段写明分母（建议 rejected/access_overflow/uplink_overflow 相对 emitted，no_route 相对 admitted-at-ingress），并在 Task 7 增加一条 RED：同一 fixture 在两种分母解释下结论不同，证明实现按声明分母计算。

### F5（major, FACT→INFERENCE）`min_directed_link_windows: 3` 不约束同一链路/连续性，无法支撑"sustained directed-link pressure"的允许结论

- 证据：计划 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L564-L568`（阈值）；`github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L62-L68`（L4 允许结论的措辞是 "sustained directed-link pressure"）。
- 推理：按字面，三条分散在不同有向链路、不同时刻的 1s 窗口各 ≥0.70 即满足 `min_directed_link_windows: 3`，但这不是任何一条链路上的"持续"压力。计划 Task 7 的 RED（"horizon-aggregate high utilization without three qualifying windows returns NO_ISL_PRESSURE"，L614）只挡聚合平均，不挡跨链路拼窗。FACT 部分是合同文本与结论措辞不一致；INFERENCE 部分是实现者大概率按字面实现而得出偏宽的 ISL_PRESSURE_CANDIDATE。
- 最小修改：改为"同一条有向链路在同一观测窗内 ≥K 个（可声明是否连续）1s 窗口 ≥0.70"，并把 RED 反例改为"三条窗口分散在三条链路 → NO_ISL_PRESSURE"。

### F6（minor, FACT）utc_start_hour 对 legacy diurnal 生效但不进 manifest 的两键 transform

- 证据：计划 vector 谓词 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L256-L264` 与边界 RED 要求 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L296`；scalar 路径 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/model.py#L517-L532`（ecef→asin 仰角）与 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/CODE/leo_sim/model.py#L529-L532`。

### F9（minor, INFERENCE/UNVERIFIED）计划未要求记录逐源接受率，alias 灾难性接受率只靠上限 fail-loud 兜底

- 证据：计划 benchmark 条款 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L435`（只比速度）；采样器 `github://fuguther/leo-direct-sim/blob/9945b794b1d090d99151e44d89e79e6f6babbe18/docs/superpowers/plans/2026-08-25-global-direct-access-scene.md#L407-L428`。
- 推理：数学上接受分布 ∝ pop^γ/max(d,floor)^α 与 scan 目标精确等价（floor^α 为常数因子，在归一化中约去；自反排除与 scan 的 same-cell 排除在 population 1:1 端点下一致）。floor=100km、α=1.25 下最坏源（远离人口团的岛屿 cell）单抽接受率约 (100/5000)^1.25 ≈ 0.008，期望 ~130 抽，10^4 上限的耗尽概率可忽略——但这是推断，未实测；若未来调高 α 或调低 floor，接受率按幂律恶化而计划无任何观测手段。
- 最小修改：benchmark 条款增加"记录全候选源的 min/mean 接受率与耗尽计数"，作为后续参数变更的对照基线。
