结论：REQUEST_CHANGES

对精确 commit 026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1 的只读 cold-start 复核结果是 REQUEST_CHANGES。

本结论是网页端 RESULT_CANDIDATE；按任务合同，最终运行验证仍由本地 Agent 完成。

F1 — retiring uplink 仍可绕过 pre-dequeue availability gates

severity: major — FACT

UplinkServer._pick() 对 active 和 retiring 两种状态的逻辑仍不对称：

active link 的 packet 在返回前检查 geometry、GE、MCS rate；

retiring link 只检查 assigned_sat == self.sat，随后直接 return p。

证据：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L273-L298

这意味着 round-2 F1 指出的 bypass 没有被关闭。

之后 _run() 会把该 packet 从 endpoint queue 移除，并占用 shared uplink server；只有进入 _transmit() 后才重新检查 geometry、GE、MCS rate。_transmit() 自身的恢复/retirement race 已经比较完整，但它发生在 dequeue 和 shared-server acquisition 之后：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L1266-L1372

Concrete reproduction

构造：

endpoint A 在 satellite S 上有 retiring GSL；

A 的队首 packet 已 assigned_sat=S；

当前 A↔S geometry down、GE down，或 MCS rate=0；

endpoint B 同样挂在 S，上行链路完全可用且有待发送 packet。

INFERENCE: DRR 可以选择 A，因为 retiring 分支不走 availability gates。A 被 dequeue 后进入 _transmit() 等待恢复/退役，从而让 UplinkServer.current 被 A 占住；B 无法利用本来可用的 shared uplink。即使最终 packet conservation 仍正确，shared-server 服务语义、queue residence 以及公平性已经错误。

Required fix

availability gates 应在 active/retiring assignment 判定之后、真正 return p 之前统一执行。retiring link 可以继续只 drain 已经 assigned_sat 的 packet，但不能因此绕过 geometry/GE/MCS 可服务性检查。

F2 — GSL exact recovery/deadline race 仍未完全实现

severity: major — FACT

F2-A：downlink zero-rate 仍退化为 time_step polling

_gsl_wait_until() 本身确实新增了 certified geometry/GE/rate/deadline wake：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L985-L1032

并且 uplink 已有非整 tick recovery regression：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/tests/test_link_budget_integration.py#L316-L346

但是 downlink 的 decision-level zero-rate 路径没有进入这个机制。_decide() 遇到 destination GSL rate=0 时直接：

mcs_zero_rate_holds += 1

pending[sat].append(pkt)

return

证据：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L2051-L2081

而 pending 的唯一常规 retry 是：

yield self.env.timeout(self.time_step)

证据：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L1517-L1523

Concrete reproduction

令：

active destination association 已建立；

geometry 始终 up；

downlink MCS 在 t<1.0 为 0，t>=1.0 恢复；

time_step=0.7；

packet 在 t<0.7 进入 _decide()。

第一次 pending retry 在 0.7，仍是 zero-rate；下一次是 1.4。因此真实 certified recovery 为 1.0，但 packet 最早 1.4 才重新获得 deliver 机会。

现有 downlink recovery test 只验证最终 delivered_at >= 1.0，没有使用不对齐 tick 来排除 polling：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/tests/test_link_budget_integration.py#L247-L273

所以 round-2 要求的“GSL exact recovery must not degrade to time_step polling” 仍不满足。

F2-B：queued GSL deadline 在 exact wake 时刻不会立即 expire

severity: major — FACT

_gsl_wait_until() 会把 packet deadline 放入 wake candidates，并只保留：

now < deadline <= horizon

证据：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L985-L1032

但 GSL queue sweeps 使用的是严格的：

now > pkt.deadline

uplink：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L1747-L1757

downlink：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/kernel.py#L1524-L1535

因此服务器被精确唤醒到 t=deadline 后：

sweep 不 expire，因为 now == deadline；

下一轮 _gsl_wait_until() 又不会再加入该 deadline，因为要求 now < deadline；

packet 只能等下一次 tick、其他 wake 或 horizon 才结算。

Concrete reproduction

令一个已在 active GSL queue 中的 packet：

链路持续 zero-rate；

deadline = 0.95；

time_step 与 0.95 不对齐；

horizon > 0.95。

server 会正确 wake 到 0.95，但 sweep 不清除 packet。其 queue residence/fate assignment 被拖到下一事件，而不是 0.95。

现有 horizon regression 只断言最终 fate，没有断言 exact expiry time 或 queue-area：

github://fuguther/leo-direct-sim/blob/026eb17cd41a2645ab58ae1b8fd0e256f1f19cb1/CODE/leo_sim/tests/test_link_budget_integration.py#L348-L369

因此它无法发现这一 race。

这里需要谨慎处理 deadline 的 inclusive semantics：正在完成 transmission / propagation 的 packet 在恰好 deadline 到达时是否允许成功，应继续遵守现有合同；需要修的是 已经确认不可服务、正在 queue wait 的 packet 在 deadline event 上不能漏掉 expiry，而不是简单全局把所有 > 改成 >=。
