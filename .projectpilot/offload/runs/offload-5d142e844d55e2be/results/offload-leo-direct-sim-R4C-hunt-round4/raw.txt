第 4 轮未知问题挖掘结果

结论：RESULT_CANDIDATE。 在精确 commit 1599d3e3c7d5d74f22ddb497969f28fe8b90b73c、且严格限定白名单路径的静态审计中，确认 3 个此前审阅文档未列出的 major 级候选问题。核心集中在 learning checkpoint/eval 证据链与失败路径奖励语义。

其中 F1/F3 会使“checkpoint 已校验”并不等价于“正在评估正确的学习合同/有效策略”；F2 会使存在链路故障的训练轨迹偏离当前明确声明的 M1 realized queue reward 语义。因此，当前 main 的学习臂尚不适合直接作为 Q0 正式科研证据链，应先做本地定向复现并修复。

绑定审阅文档中已经明确记录的 comparison 资源不等价、experiment_platform NaN、CSV 微秒量化、future-endpoint 侧信道、TabularQ unseen-state tie 等问题均未重复计数。证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/ANALYSIS/EXPERT-REVIEW-20260816.md#L133-L154

F1 — 同宽 learning contract 的 checkpoint 可跨合同加载，并被重新标记为当前 contract

严重度：major
判定：FACT（静态控制流可证；DDQN 需 TF 主机做动态确认）

C3 与 C4 虽然表示语义不同——C3 是普通 mean aggregate，C4 是 AoI-weighted aggregate——但二者具有完全相同的输入宽度。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L50-L64

DDQN checkpoint 加载时只验证：

文件 SHA；

input shape；

output shape。

没有验证产生 checkpoint 时的 contract。因此 C3 模型在 C4 下形状检查天然能够通过。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L331-L351

TabularQ 更直接：checkpoint 中甚至没有 contract 字段，加载仅检查 SHA、entries 是否 list、以及每行是否恰有 5 个 action Q 值。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L610-L630

运行结束时又使用当前 learner 的 contract生成 diagnostics，并可重新保存 checkpoint，因此错误来源的 checkpoint 会得到当前合同标签。Kernel 正是通过 diagnostics()/save_and_verify() 生成最终 learning ledger。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/kernel.py#L1760-L1778

最后一道 receipt 门也没有检查 learning.contract == resolved_cfg.routing.contract，只检查 algorithm、mode 合法值、计数、checkpoint SHA、eval 是否训练等，因此不能发现跨合同来源。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/receipt.py#L418-L519

最小复现：

训练并保存 C3 checkpoint；

用其精确 SHA 配置 C4 eval；

DDQN：C3/C4 同 input/output shape，加载门不会拒绝；

Q-learning：当前 checkpoint 根本没有来源 contract；

C4 observation 随后被送给 C3 学到的策略；

输出 diagnostics/metadata 却会报告当前 "contract": "C4"。

影响： 表征消融、学习臂比较和正式 eval 可以在文件 SHA 完全正确的情况下评估错误表示语义的模型；最终 artifact 还可能看起来已经完成 save/load verification。这属于科学归因级错误，而非单纯 metadata 缺失。

F2 — Forward 的 realized M1 queue reward 在终态失败路径被统一覆盖成 0

严重度：major
判定：FACT（控制流可证）；未在本任务执行环境动态实跑

当前代码明确在 ISL 真正开始 service 的瞬间计算并写入 realized M1 queue reward：

pkt.learning_reward = queue_reward(realized_queue_wait, ...)

证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/kernel.py#L899-L910

现有永久回归测试也把该语义写得很明确：forward action 应取得由实际 queue wait 决定的 M1 reward；零等待时就是 w1=20。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/tests/test_reward_migration.py#L148-L166

但如果 service 开始后发生 geometry loss、GE outage 或 deadline 等失败，_transmit() 随后调用 _fail(pkt, fail_kind)：
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/kernel.py#L930-L942

而 _fail() 对所有 DataPacket 均强制：

terminal_reward=0.0

_finish_learning_transition() 又规定显式 terminal_reward 优先于已经存在的 pkt.learning_reward，因此刚刚实现的 M1 reward 被覆盖掉。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/kernel.py#L1639-L1668
以及：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/kernel.py#L1409-L1434

最小复现建议：

构造 2 星单 ISL 场景，学习器用现有 _StubLearner：

forward E；

queue wait = 0，所以 service start 时应结算 M1 reward = 20；

令 ISL 在 service 中途发生 geometry loss；

当前控制流最终 remember("E", 0.0, done=True)，而不是保存已经实现的 20。

同样应覆盖 GE failure、ISL propagation 阶段 deadline、到达下一星后 NO_ROUTE 等终态。

影响： 成功 forward 得 M1 queue reward，失败 forward 在同样已经支付过排队成本后却被改写为 0。高故障/高 deadline 压力训练下，reward distribution 会系统性改变，训练结果、策略选择和不同故障设置之间的归因均受影响。

如果产品设计确实希望“任何失败 forward 的最终 reward=0”，那也应把它明确写成 terminal-loss reward 合同并增加回归测试；以当前注释和现有 M1 测试定义看，它属于语义漂移。

F3 — TabularQ 可接受结构无效的 pinned checkpoint，并将其“洗”为 checkpoint_verified=true

严重度：major
判定：FACT（静态控制流可证）

TabularQ loader 对 checkpoint 的语义结构检查不足。它没有检查：

checkpoint schema；

state-key 的字节长度是否等于当前 contract observation 的 float64 宽度；

重复 state key；

Q 值的有限性等更强约束。

只要 entries 是 list，且每个 value row 有 5 个元素，就会插入 table。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L610-L630

但运行时真实 state key 是整个 observation 的 float64 原始字节。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L637-L656

因此类似以下语义无效但 SHA 完全正确的输入即可进入 loader：

schema="bogus"，state key 仅 "00"，Q row 为 5 个普通数值。

该 1-byte key 永远不可能等于正常 C3/C4 observation 的完整 float64 key。eval 因而把全部实际状态视为 unseen，并进入已经存在的 deterministic zero-row fallback。

更严重的是，save_and_verify() 随后会：

用当前 canonical schema重新输出这张 table；

仅重新 JSON load 并比较相等；

设置 checkpoint_verified=True。

证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L690-L735

receipt 对最终 Q-learning artifact 也只重新计算文件 SHA，没有检查内部 state key/schema 与 contract 的一致性。
证据：github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/receipt.py#L471-L519

影响： “文件完整性正确”被错误提升为“checkpoint 语义有效”。错误/旧格式/第三方生成的 q_table 可以被当前系统重新序列化为 canonical schema，并获得 verified 标志；真实 eval 则可能全部退化到 unseen-state fallback。H2-19 已知的是 fallback 的首合法动作 tie 偏置；本项新增问题是无效 checkpoint 能静默触发并通过 artifact verification，两者不是同一缺陷。
