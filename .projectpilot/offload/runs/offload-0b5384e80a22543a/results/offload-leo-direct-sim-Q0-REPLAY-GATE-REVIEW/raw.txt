RESULT_CANDIDATE — REQUEST_CHANGES

绑定 commit：a81a16563758890115a258556edf6d8c87884e02

结论：当前实现不应作为第一阶段 Q0 execution replay gate 放行。 基础机制已经能在简单 FORWARD 场景中区分“计划入队”和“真实 _transmit 启动”，普通 validation-failure 原子性也基本成立；但存在两个可导致 replay 假绿的实质缺口：跨卫星 DELIVER 可被合法化并通过 gate，以及 execution audit 没有绑定具体 Q0 action，后续内核重决策产生的相同服务事件可以追认旧计划。此外还有重复动作匹配、WAIT NaN 与证据导出不足问题。

F1 — blocking：DELIVER 未绑定 packet 当前 pending 卫星，可“瞬移”后被 replay gate 认证

FACT

_data_packet_locations() 明确保存了 pending packet 所在卫星，因此校验器知道 packet 的真实当前位置：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1158-L1164

进入 validate_joint_plan() 后，所有 action 已要求 packet 是 pending。FORWARD 显式检查 action.sat != location[1] 并拒绝错误卫星；WAIT 也做同样检查。但 DELIVER 分支没有检查 action.sat == location[1]，只检查目标 endpoint 在 action.sat 上存在 active link、可见且 downlink 有容量：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1232-L1261

应用阶段进一步确认了问题：packet 是从其实际 pending satellite 删除，然后直接放入 action.sat 的 downlink。因此若两者不同，中间没有任何传播过程：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1283-L1310

真实 downlink 服务随后会以这个目标 satellite 记录 "deliver" execution，而 verifier 只比较 kind/packet_id/sat/direction：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1338-L1388

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1515-L1527

设计合同要求 packet 位置与快照一致，并禁止绕过真实物理过程：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/ANALYSIS/Q0-INTERFACE-DESIGN-20260817.md#L63-L76

INFERENCE

若 packet 当前在 satellite A 的 pending[A]，而 destination endpoint 同时在 satellite B 上存在合法 active association，则 DELIVER(pid, B) 会通过校验；apply 会直接从 A 删除并加入 B 的 downlink；之后 B 上真实 GSL service start 会形成匹配 execution audit，verify_q0_replay() 可以返回成功。

这不是“只是验证器太宽松”：它是物理位置越权 + replay 假阳性。

UNVERIFIED

受任务合同限制未运行该反例；测试文件也没有 wrong-satellite DELIVER 回归。

是否阻塞第一阶段 Q0 execution gate：YES，blocking。

F2 — blocking：execution audit 没有 action 因果身份，后续自主重决策可以追认一个从未启动服务的旧 Q0 action

FACT

_record_q0_execution() 的记录只有：

kind

packet_id

sat

direction

executed_at

没有 plan version、plan hash、action ordinal/action ID，也没有“当前 service 是由哪个 q0_replay_expected queue insertion 导致”的 token：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1338-L1347

而且它不是 Q0 专属 hook；任何 DataPacket 的 ISL/downlink _transmit 真正开始时都会无条件调用：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1515-L1527

存在一条明确的“Q0 queue insertion 被取消、没有 service start”的合法内核路径：downlink packet 如果在启动服务前失去 association，会从 downlink queue 弹回 pending：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L495-L508

之后 pending ticker 自动触发重决策：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1624-L1631

_redecide_pending() 会调用普通 _decide()：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L2247-L2252

如果 endpoint 后来又在同一个 satellite 上 active，普通内核 _decide() 可以再次将该 packet 放入相同 downlink：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L2160-L2186

而 verifier 只寻找相同 packet_id/kind/sat/direction 的 execution，并要求执行时间不早于 submission；它不验证该 execution 是否仍属于原始 queue insertion：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1356-L1388

INFERENCE

可以形成：

Q0 DELIVER insertion → association 丢失 → 原 insertion 被退回 pending（零 service start）→ kernel 自动 re-decide → later DELIVER at same sat → real service start

最后那个自主动作的 execution event 会满足旧 Q0 expectation。

因此当前 gate 证明的只是：

“提交之后某时刻曾出现过相同 tuple 的 service start”

而不是：

“这个 Q0 action 的 queue insertion 确实到达了真实 service start”。

这正是 replay gate 最需要排除的假阳性。

UNVERIFIED

事件序列的具体 SimPy 调度反例未在本任务执行；上述各状态转换路径均直接存在于绑定代码。

F3 — major：重复 packet/action 历史中，greedy matcher 会先匹配旧 execution，再报 execution precedes plan，即使后面存在正确 execution

FACT

verify_q0_replay() 为 forward/deliver 使用 used 做一对一消费，这是正确方向；但查找时：

从 execution audit 开头开始；

找到第一个未使用的相同 tuple 就 break；

之后才检查 executed_at < submitted_at。

它不会在发现旧 execution 后继续搜索新的合法 execution：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1356-L1388

同时 JointPlan 只禁止同一份 plan 内一个 packet 出现两次，并没有禁止 packet 在后续 plan 中再次行动：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/q0.py#L53-L68

再结合 F2：execution audit 本身包含非 Q0 action 的 service start。

INFERENCE

历史中若已有一个相同 (pid, kind, sat, direction) execution，之后提交 Q0 action，并且该 Q0 action 后来也确实启动了服务，matcher 仍可能先抓住旧 event，然后报告 "execution precedes plan"，不会使用后面的正确 event。

这是 false negative，不是安全假阳性，但说明 repeated packet actions 尚未被可靠处理。

UNVERIFIED

未运行循环/重复 action 反例。

是否阻塞第一阶段 Q0 execution gate：YES，作为通用 repeated-action gate 会错误拒绝合法 replay；但它本身不是假绿。

F5 — major：WAIT(until=NaN) fail-open，并且会立即获得 replay “execution” 记录

FACT

PlanAction 对 WAIT 只要求 until 是 int/float，没有 math.isfinite()，因此 float("nan") 可以通过构造：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/q0.py#L43-L50

Kernel 校验使用：

until <= now 或 until > horizon

NaN 与两者比较均为 false，因此不会进入 invalid WAIT deadline：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1262-L1273

WAIT 在 apply_joint_plan() 中直接设置 holding_until，并在同一个 apply 调用内立即写入 "wait" execution audit：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1310-L1328

verify_q0_replay() 对 WAIT 只要求找到同 packet/sat、且 execution time 等于 submitted time 的该 inline audit：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L1358-L1369

而 holding queue 的释放条件是 now >= holding_until；对 NaN 永远为 false：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/kernel.py#L192-L201

INFERENCE

Malformed WAIT(NaN) 可以：

validate=True → apply=True → wait execution audit 写入 → verify=True

但 packet 永远不会因 until 到达而变 ready。对包含 WAIT 的 Q0 replay，这属于明确的 fail-open。

测试充分性

现有 replay 测试只覆盖一个单次 FORWARD happy path 和一个“apply 后立刻 verify”的无 execution 情形：

github://fuguther/leo-direct-sim/blob/a81a16563758890115a258556edf6d8c87884e02/CODE/leo_sim/tests/test_q0_contract.py#L116-L147

缺少以下关键 mutation/regression：

wrong-satellite DELIVER

DELIVER 入队后 association 丢失→pending→自动重决策→相同 later service

同 packet/sat/direction 多轮历史，且存在 pre-plan matching execution

repeated WAIT

WAIT(NaN)

run() 返回 artifact 的 replay evidence/schema 断言

这使当前两条 replay 测试不足以覆盖 gate 的真正高风险边界。

建议本地 Agent 的最小整改门槛

DELIVER 与 FORWARD/WAIT 一样强制 action.sat == location[1]。

为每个 applied action 生成稳定 action_id/plan_id + ordinal；该 identity 必须随 packet 的该次 queue residency 一直传到 service-start audit。queue residency 被取消/退回 pending 时，该 action 应显式记为 cancelled/diverged，而不能由后续自主动作补票。

matcher 至少按 executed_at >= submitted_at 参与候选筛选，不要匹配后再检查；repeated action 要严格一对一。

WAIT 的 until 要强制 finite；WAIT replay 应明确验证的是 holding admission 还是完整 until 行为。

导出 plan hash、action ID、expected、matched execution、gate verdict/errors、first divergence；不要只导出两份裸 list。

增加上述反例测试后，由本地 Agent 实际执行测试与定向 replay。
