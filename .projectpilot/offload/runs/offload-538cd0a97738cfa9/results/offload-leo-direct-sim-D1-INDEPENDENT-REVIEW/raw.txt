推理链：

因此当前对象处于一个内部矛盾状态：

从 _transmit / occupied 语义看：尚未服务；

从 queue/queue_area 看：已经离队；

从 server 调度看：已经成为 current，server coroutine 被该包占住。

这会产生三个实际后果。

第一，queue_area_bits_s 不包含 zero-rate cold wait。尤其 ISL 学习奖励仍保留 pkt.isl_enqueued_at，直到真正 transmission start 才按 t_start - isl_enqueued_at 计算实际 queue wait。也就是说，同一段时间学习奖励认为是排队等待，而 queue_area 诊断认为已经不在队列。
证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L1245-L1285

第二，对于每星共享的 Uplink/Downlink server，某一 endpoint 的 MCS=0 后，整个 _run() coroutine 会阻塞在这个包的 yield _transmit(...) 上。即便另一个 endpoint 与同一卫星的当前 MCS>0，也不能被 DRR 服务，形成零速率 endpoint 对其他可服务 endpoint 的 head-of-line blocking。若 D1 的语义真是“该 link down”，正确调度应至少允许 shared server 考察其他可服务 endpoint，而不是让一个不可服务流独占 server。

第三，队列容量会因这个 pre-service current 被移除而释放。这里我把结论限定为“与设计稿的‘仍在队列’定义不一致”，而不武断断言所有 queue-capacity 定义都必须包含 server-current；但从本 PR 自己给出的 cold-start 合同看，现实现至少需要明确重定义，否则 queue occupancy、area、room 和服务相位不在同一口径。

可复现条件：

最强复现场景是同一 satellite 两个 GSL endpoint：

A 当前 RF/MCS rate=0；

B 当前 rate>0；

两者均有包；

DRR 先选 A。

预期“link-down”语义下 B 应仍有机会用共享链路；当前实现 A 会占住 server 直到 rate recovery/deadline/horizon。

影响：

queue_area 系统性低估 cold-start congestion；

shared GSL 产生额外 HOL blocking；

学习奖励与诊断队列面积对“等待”的定义不同；

可能改变拥塞、时延和 overflow 行为，而不仅仅是 diagnostic 输出。

与 D1 目的关系： D1 原目标是用动态速率逼近 legacy link semantics；当前实现把“单 link 无速率”扩大成“整个共享 server 无服务”，可能反而引入新平台特有阻塞机制。

也就是说 receipt 会说 MCS 没有 effective，实际正是 MCS gate 改变了 fate。

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L868-L893

但 config 无论 constant 还是 mcs 都会：

强制 mcs_table == legacy-dvbs2x

强制三套 RF 拥有 exact key set

强制所有字段 finite、positive。

只有 min-MCS/min-rate 组合检查才受 rate_model=="mcs" 保护。
证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/config.py#L510-L554

Kernel 初始化也无条件构造三套 RFParams 并计算三个 max_rate_range_km。
证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L728-L759

所以“constant 完全不碰 RF/MCS”并不成立。尤其设计稿原话是 constant 下 RF“忽略”。
证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/ANALYSIS/LINK-BUDGET-DESIGN-20260816.md#L40-L65

影响： 正常默认配置不会因此改变 packet timing，但一个实际上永不使用的 RF 配置仍可令 constant config fail；初始化也承担无用的 RF 数学失败面。若目标真的是“constant old behavior isolation”，应把 RF validation/derivation 放进 mcs 分支，或者正式修改设计合同为“constant 不使用 RF 产生 rate，但 resolved config 仍严格验证 RF”。

未验证： 我没有读取前一 commit，因此不能宣称 archived old receipt 一定被破坏；不过当前 receipt/requested schema 已显式包含 rate_model/mcs，历史工件兼容性应由本地 Agent 用旧 fixture 验证。

F6 — minor：硬退役若在 service/wait 已开始后才被安排，恰与 completion/deadline 同刻时，代码的“retirement tie wins”并非总成立

严重度：minor；处置：增加同刻竞速测试并修正。

FACT： _transmit() 在每次 while 开头读取一次本地变量 retire_t。若 link 当时还是 active，retire_t=None。之后 service 会 yield timeout | interrupt。只有：

Python
运行
env.now < fail_t - 1e-12

时才重新计算整场 race。若 interrupt 恰在原 fail_t 同刻到达，则条件为 false，仍按旧 fail_kind 返回。
证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L1150-L1325

而 access tick 可以在 service 已开始后把原 active link 改成 retiring，并未来才 schedule _fire_interrupt(retire_at)。
证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L1430-L1495

因此：

若 retire_at == service completion，可能走 "ok"；

若 retire_at == deadline 且旧 race 已选 deadline，可能先记 deadline fate；

只有 retirement 在本轮 race 构造时已经 known，retire_t <= fail_t 才稳定让 retire 赢。

这与 _transmit() 内注释所声明的 tie policy 不完全一致。它并非 D1 独有，但 D1 增加的长时间 zero-rate wait 提高了“service/wait 开始后 link 再进入 retiring”的暴露机会。

3. 对抗：主动攻击上述结论
3.1 对 F1 的反例：也许正常仿真从不会在 waiting_for_link 中调用 snapshot？

这是 F1 最强替代解释。

FACT： server 在 _transmit() 内 yield 到未来 recovery/deadline 后，current/_svc_phase/_service_rate_bps 状态会持续存在；不是一个无法观察的同函数局部瞬间。

INFERENCE： 只要 Q0 驱动器允许在事件步之间读取当前全局状态，就存在合法调用窗口。snapshot 本身又没有文档声明“waiting_for_link 时禁止调用”。

因此不能用“通常 planner 恰好不会在这个时刻读取”消除接口错误。即便上层目前没命中，支持的 snapshot 函数仍不应对一个 kernel 自己产生的正常状态除零。

结论：F1 major 不降级。

3.2 对 F2 的反例：server-current 本来就不属于 queue，queue capacity 释放是标准排队论口径

这个解释部分成立，所以我修订了表述。

如果系统把“queue”严格定义为等待 buffer，不含 server-current，那么 dequeue 后 queue capacity 释放本身并不能独立证明 bug。

但这里还有三条证据排除了完全免责：

D1 设计明确说零速率时“包排队等待恢复”；

_transmit 明确说 transmission 尚未开始；

ISL learning 的 queue reward 继续把这段时间算入 realized queue wait。

与此同时 queue_area 却不计入，shared GSL server 又被 current 阻塞。

因此我不再声称“任何 queue capacity 都必须包含该包”，但保留“当前 PR 内部存在至少三种互相冲突的等待定义”和 shared-GSL HOL 的 major 结论。

F2 major 保留，但论证范围收窄。

3.3 对 F3 的反例：mcs_rate_samples 也许故意只定义为“正速率 samples”

如果真如此，名字虽不理想，但是否仍能作为 effective 依据？

不能。

因为 _transmit() 在 geometry/GE down 时仍会执行 rate_fn()；只要 rate 正数就递增，所以一个根本没开始 service的包也可令 mcs effective=true。相反，MCS=0 明确阻止 service 并导致 deadline 时却不计数。

因此它既不是：

全部 MCS query 数；

实际 service-start MCS 数；

MCS 对结果产生作用的次数。

三个合理定义都对不上。

同样，control_tx_started 若被解释为“server dequeue started”，又与 receipt 字段名 transmission_started 和 _transmit 的 waiting_for_link 语义冲突。

F3 major 不降级。

3.4 对 F4 的反例：设计稿其实说“capacity routing 动态 rate 另行评审”，所以 D1 本来就不负责路由

这是 F4 最有力的降级理由。

FACT： 设计稿确实没有要求把动态速率直接作为所有 routing cost；capacity/routing 使用动态速率被留作额外评审。

但这里的问题并不是“是否把 1.81 Gbps 和 0.99 Gbps 精细比较后选更快的路”。问题是0 bps 是否仍属于当前可执行动作。

同一设计稿又明确写：

旧侧 0-rate edge 天然不可用；

D1 零速率语义“等同 link down”。

因此不需要让 routing policy 使用全部速率值，也可以只在 Kernel final legal mask 做一个当前 rate>0 的物理可行性 gate。这个 gate 不需要未来信息，也不是 capacity-routing policy 改造。

所以若 PR charter 明确宣称“D1 只改 server，完全不承诺零速率动作集合”，本地 Agent 可以考虑把 F4 降为 minor/design follow-up；但按当前设计文本和“向 legacy 靠拢”的目标，我仍判断 major。

3.5 未验证假设清单

以下没有被包装成事实：

未验证： 三套 RF 参数与旧平台原始 Python 源逐字段一致；旧源不在授权范围。

未验证： 真实 66 星 Walker 场景中，有多少时间实际 ISL 落入 5826.8–6000 km 壳层；需要本地统计。

未验证： routing.choose_next_hop() 对每种 policy 如何排序 MCS-zero candidate；routing.py 未获授权。

未验证： 历史 constant-mode receipt fixture 是否要求由新 verifier 继续接受；前一版本工件未获授权。

未验证： 本 commit 的完整测试套在真实环境是否全绿；合同禁止我执行本地 Shell。

未验证： SimPy 同刻 event 的具体 callback 排序会让 F6 的哪一种结果先发生；但无论具体顺序，当前 env.now == fail_t 时不会进入“recompute race”分支这一代码事实成立。

4. 修订：对抗后的最终判定

对抗前我的候选结果是 4 major + 2 minor。对抗后没有发现足以撤销 major 的反证，但对两项结论做了范围修订：

F1：major → major，不变。 零速率 snapshot 除零是直接、可达的代码路径。

F2：major → major，但缩窄。 不再把“current 不计 queue capacity”本身普遍定义为错误；最终 major 依据是 PR 自己的排队合同、queue_area 与 learning wait 不一致，以及 shared GSL HOL blocking。

F3：major → major，不变。 receipt key/hash 结构层被确认是闭合的，因此问题从“verification bypass”修订为“kernel 原始 testimony 语义错误且 verifier 无法独立纠正”。

F4：major → major，保留条件说明。 若 D1 正式 scope 明确排除 physical legal-mask，则可由本地 Agent 降级；按现有设计稿“0-rate 等同 down”和 legacy 目标，仍应合并前修。

F5：minor → minor。 正常 constant transmission timing 看不到动态 rate；问题限于 validation/init/compatibility surface。

F6：minor → minor。 是精确同刻竞速角落，不足以上升 major，但应增加 deterministic tie test。

最终判定

REQUEST_CHANGES。

不是因为 FSPL/SNR/MCS 数学主体失败；恰恰相反，数学主体是本 PR 最稳的一块。阻碍批准的是：从“得到 rate=0”以后，kernel 没有形成一个统一的 not-yet-in-service 状态模型。

当前同一个 zero-rate packet 同时表现为：

_transmit：没开始服务；

occupied：没占服务时间；

queue_area：已经离队；

server：已经 current 并阻塞；

snapshot：尝试拿 0 bps 算 service residual；

control receipt：可能已经 transmission_started；

MCS receipt：却可能 effective=false；

routing：仍可能把该 edge 当 legal。

这组矛盾说明 cold-start 不是一个局部边界 bug，而是 D1 需要补完的状态机合同。

5. 收尾：open_items、下一步与实际审计面
5.1 建议的修复顺序

P0 — F1：重新定义 snapshot 的 waiting 相位。
建议 waiting_for_link 时不要把 remaining_service_s 伪装成确定的未来 service duration。至少应：

暴露 remaining_bits；

暴露 current_rate_bps，允许为 0；

remaining_service_s 在尚未真正起传时设 None，或者另建明确命名的 if_started_now_service_s；

transmitting 后才以固定 sampled service rate 计算真正 residual。

这同时解决除零和陈旧 rate 问题。

P0 — F2：把 MCS-zero gate 移到 dequeue/serve eligibility 前，或建立明确 blocked-pre-service 状态。
对于共享 GSL server，优先方案是 DRR 只选择“当前 geometry/GE/rate 均可起传”的 endpoint；一个不可服务 endpoint 不应阻塞其他 endpoint。ISL 若保留 head blocking，则 zero-rate head 应仍按 PR 定义留在 queue/area，直到真正可起传。

P0 — F3：拆分 counters。
至少考虑：

mcs_rate_queries：每次调用 rate_fn 都计，包括 0；

mcs_zero_rate_waits：MCS gate 实际阻止服务；

mcs_service_starts：真正起传且 rate 用于 dur；

control_tx_started 移到 _transmit 将 phase 切为 transmitting 的唯一位置。

然后明确 effective.mcs 的含义。如果“mechanism 被实际 consult”就是 effective，则 mcs_rate_queries>0 最直接；如果要求“影响了服务”，则可用 zero_rate_waits + service_starts > 0。

P0 — F4：把当前零 MCS 纳入物理 legal mask。
不要求修改 routing cost，只需在最终 legal action 过滤时，在 rate_model=mcs 下要求当前 _link_rate(...)>0。这仍只读取当前 slant range，不引入 future geometry。GSL deliver 合法性也建议按同一合同处理。

P1 — F5：决定 constant 配置合同。
二选一：

真正“ignore RF”：constant 不校验 unused RF/table，不构造 RFParams，不计算 max range；

保留 canonical strict config：那就修改设计文档，明确“constant 不使用 RF 改变服务，但 resolved config 仍绑定并验证 RF”。

不要同时声称两者。

P1 — F6：统一 retirement tie。
任何 wait | interrupt 返回后，在处理 completion/deadline 前重新读取：

当前 link state；

当前 retire_at;

若 now >= retire_at，应先执行既定 retirement tie policy。不要只依赖进入当前 while iteration 时缓存的 retire_t。
