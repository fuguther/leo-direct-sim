终审结论

终判：REQUEST_CHANGES。

四个 R4A2 原始问题中，F1 的“静态重写 sibling metadata 即重标 contract”主漏洞、F2 非法 UTF-8、F2(独立) key 宽度/唯一性/Q finite、F3 payload mapping/schema 等核心实现均已补上。

但本轮发现一个新的 major：现代 TabularQ checkpoint（payload 已含正确 contract）在配置了 checkpoint_metadata_sha256 时，loader 会直接忽略这个 pin；receipt 却会事后要求它匹配。 因此形成：

config 接受 metadata pin → TabularQ loader 不验证 → eval 已开始运行 → receipt 最后才拒绝

这不满足本任务要求的“checkpoint_metadata_sha256 在 config / DDQN+TabularQ loader / receipt 三处强制生效”，不建议合并。

1. F1：sibling metadata 可重标 contract
结论：原始攻击路径基本闭合，但 TabularQ metadata-pin 语义仍不完整

FACT — 已修复部分：

checkpoint_metadata_sha256 已进入 config schema，并校验为 64 位 lowercase SHA-256；ddqn + eval 在 checkpoint path/SHA 校验之后继续强制要求 metadata pin，因此不存在“先满足 checkpoint SHA 就跳过 metadata pin”的校验顺序漏洞。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/config.py#L526-L560

DDQN 加载时先校验 checkpoint SHA，再强制读取 sibling metadata.json，校验 metadata 自身 SHA pin，随后交叉校验 schema / algorithm / contract / checkpoint / checkpoint_sha256 / checkpoint_verified。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L72-L133

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L397-L425

Legacy TabularQ（payload 没有 contract）也只能在 sibling metadata 存在、非 symlink、metadata SHA 被 config 独立 pin，并通过完整 metadata 字段验证后迁移。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L708-L727

新增回归测试确实先取得原 metadata SHA，再把 contract 从 C3 改成 C4，随后要求加载因 metadata SHA 不符失败；这个测试真实覆盖了 R4A2 的“只改 sibling metadata 重标”负例。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_qlearning_migration.py#L310-L323

receipt 对 DDQN、Q-learning eval 均会把 ledger 中 loaded_checkpoint_metadata_sha256 与 resolved config 的 pin 比较；同时两种算法均检查 learning.contract == routing.contract。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/receipt.py#L420-L537

新发现 N1 — major：现代 TabularQ 忽略显式 metadata pin

FACT： TabularQ 只有在 payload.get("contract") != self.contract 的 legacy 迁移分支才调用 _read_checkpoint_metadata()。当现代 payload 自带正确 contract 时，这整个 metadata 验证分支不会执行。

加载结束后，该路径还明确把：

loaded_checkpoint_metadata_sha256 = None

而不是 config 中提供的 pin。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L690-L768

FACT： config 并不禁止 Q-learning eval 设置 checkpoint_metadata_sha256；只有 DDQN eval 强制要求它。因此“现代 Q-learning + 显式 metadata pin”是合法 resolved config。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/config.py#L526-L560

FACT： receipt 在 Q-learning eval 中，只要 config 的 checkpoint_metadata_sha256 非空，就要求 ledger 的 loaded_checkpoint_metadata_sha256 与它相等。因此上述合法配置会在 loader 阶段通过，却在 receipt 阶段因 None != expected_meta 被拒绝。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/receipt.py#L490-L537

更关键的是，现有现代 Q-learning roundtrip 测试确实给 loader 传入了 metadata pin，但只检查 table 内容，没有断言 loaded_checkpoint_metadata_sha256，所以这个缺陷被测试掩盖了。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_qlearning_migration.py#L101-L149

INFERENCE： 当前状态不属于静默生成“通过 receipt 的错误研究结果”，因为 receipt 最终会挡住；但它违反 fail-closed load contract，并允许使用一个声称 metadata 已 pin、实际上从未验证的配置启动 eval。这足以构成 major / REQUEST_CHANGES。

建议：只要 Q-learning config 中 checkpoint_metadata_sha256 非空，无论 payload 是否已经含 contract，loader 都应验证 sibling metadata 并记录实际已验证 metadata SHA。Legacy 路径仍应强制非空 pin。

2. F2：metadata 非法 UTF-8
结论：已修复

FACT： _read_json_utf8() 同时捕获：

OSError

UnicodeError，包含 UnicodeDecodeError

json.JSONDecodeError

并统一转换为 LearningUnavailable。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L105-L114

该 helper 同时被：

DDQN / legacy Q-learning sibling metadata

Q-learning checkpoint payload

使用，因此非法 UTF-8 的 metadata 和 payload 静态路径都会转换成 LearningUnavailable。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L117-L133

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L695-L703

新增测试用真实非法 UTF-8 bytes 覆盖 metadata 路径，并要求异常类型为 LearningUnavailable。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_qlearning_migration.py#L326-L337

测试缺口： 允许测试中没有单独的“q_table payload 非法 UTF-8”用例。实现共享同一 helper，因此这是测试覆盖不足，不是当前实现缺陷。

3. F2(独立)：legacy TabularQ state-key / representation
结论：要求中的核心校验均已实现

FACT：

加载端现在：

先要求 schema discriminator 精确等于 leo-sim-qlearning-table/v1；

entries 必须是 list；

每项必须为二元 [key_hex, values]；

key 必须能 bytes.fromhex()；

key 字节数必须严格等于 CONTRACT_DIMS[self.contract] * 8；

解码后的 key 必须唯一；

Q row 必须转换为 float64 后 shape 严格等于动作数；

所有 Q 值必须 finite。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L699-L763

错误宽度测试明确制造 16-byte state key，而 C3 所需为 CONTRACT_DIMS["C3"] * 8，并要求 LearningUnavailable("state key width...")。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_qlearning_migration.py#L286-L307

FACT： duplicate state key 和 NaN Q value 也有负例。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_qlearning_migration.py#L340-L368

一个轻微严格性问题是 bytes.fromhex() 接受非 canonical hex 表示（例如空格/大小写），而 saver 输出的是 key.hex() 的 canonical 连续 lowercase 形式；但解码后 bytes 相同，且唯一性按 bytes 检查。按本任务明确列出的验收条件，不把它升级为阻塞项。

4. F3：TabularQ payload schema
结论：核心问题已修复

FACT：

payload 非 mapping → LearningUnavailable

schema discriminator 错误 → LearningUnavailable

entries 非 list → LearningUnavailable

malformed entry → LearningUnavailable

重复 state key → LearningUnavailable

Q row shape 不符或 NaN/Inf → LearningUnavailable

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L699-L763

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_qlearning_migration.py#L340-L368

N2 — minor：不是“精确 top-level key set”schema

FACT： loader 验证了 schema 字符串及必要字段，但没有检查：

set(payload) == {"schema", "contract", "entries"}

或 legacy 的精确字段集。因此任意未知顶层字段会被忽略。

Saver 本身只产生 schema / contract / entries 三字段。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L840-L871

INFERENCE： 如果 R4A2 所说“payload schema”仅指 schema version discriminator，则 F3 已闭合；如果要求类似 receipt/config 的严格 unknown-field rejection，则仍有 minor 缺口。它不改变当前 contract/Q-table 语义，因此不单独阻止合并，但建议明确契约。

5. 测试强度与 config 校验顺序

FACT：config 顺序正确。 当 DDQN eval 已提供合法 checkpoint_path + checkpoint_sha256 后，代码仍继续检查 checkpoint_metadata_sha256 is None 并拒绝，不存在被前一分支短路掉的漏检。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/config.py#L548-L560

但允许范围内的 test_config.py 只测试了：

DDQN eval 完全没 checkpoint path/SHA；

checkpoint SHA 格式非法。

没有“path + 合法 checkpoint SHA 都存在，但 metadata pin 缺失”的直接回归测试。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/tests/test_config.py#L62-L77

因此实现目前正确，但测试没有锁住这条最关键分支。

6. 独立边界检查：hash 后重新打开文件
N3 — 条件性风险，暂不作为终判主因

FACT： metadata helper 对同一路径执行两次独立读取：

path.read_bytes() 用于 SHA；

_read_json_utf8(path, ...) 再次打开并解析。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L117-L133

Q-learning checkpoint 也是先 read_bytes() 哈希，再重新 read_text() 解析；DDQN 则先哈希 checkpoint 文件，再让 Keras 从 pathname 重新加载。

证据：

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L397-L414

github://fuguther/leo-direct-sim/blob/44f6963f0a1f0a63f6c9d02cb67d074ee1b52f53/CODE/leo_sim/learning.py#L690-L703

INFERENCE： 若 checkpoint trust model 包含“另一个进程可在验证期间并发替换文件”，则存在典型 hash-then-reopen TOCTOU：被解析/加载的 bytes 不一定是被 SHA 验证的 bytes。当前允许文件无法证明该并发攻击是否属于正式威胁模型，因此不以此把终判升级为 BLOCK；应由本地 Agent 明确 threat model，并最好改成“同一份 bytes 完成 hash + decode/parse”。

处置建议

在合并前至少修 N1：现代 Q-learning eval 只要 config 提供 metadata pin，就必须真正验证 sibling metadata 并把已验证 SHA 写入 diagnostics。随后增加三个直接回归测试：现代 Q-learning 错误 metadata pin 必须在构造 learner 时失败；现代 Q-learning 正确 pin 后 loaded_checkpoint_metadata_sha256 == config pin 且 eval receipt 能通过；DDQN eval 在 path+合法 checkpoint SHA 已提供但 metadata pin 缺失时必须由 config 立即拒绝。

之后建议再补 payload invalid UTF-8 独立测试，以及决定是否要求 exact top-level payload key set。若 threat model 包含并发文件修改，再一并消除 hash/read 分离。
