F1 — DDQN checkpoint 只绑定 SHA/shape，不绑定原始 learning contract，可把 C3 checkpoint 静默重标为 C4

严重度：major
状态：FACT（代码路径）；完整 CLI/receipt E2E 未执行。

证据

C3 与 C4 的 observation 维度完全相同，但语义不同：

C3_DIM = OWN_FEATURES + ORIGIN_FEATURES

C4_DIM = OWN_FEATURES + ORIGIN_FEATURES

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L33-L52

实际构造时，C3 对来源状态做普通均值，而 C4 用 AoI 指数权重平均，因此同一坐标位置代表不同的状态映射：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L985-L1023

但 DDQN 加载 checkpoint 时只做：

文件存在；

checkpoint SHA 与 resolved config 一致；

Keras input/output shape 与当前 contract 尺寸一致。

没有读取 checkpoint 的 sibling metadata.json，也没有校验 checkpoint 原始 schema / algorithm / contract：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L315-L355

Kernel 又直接把当前 routing.contract 传进 learner：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/kernel.py#L590-L628

更关键的是，运行结束重新保存时，metadata 中的 contract 来自 self.contract，即当前配置，而非 checkpoint 原始 provenance。因此一份 C3 checkpoint 在 C4 eval 中通过 shape 检查后，会被输出 metadata 重新标成 C4：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L530-L566

receipt verifier 检查 algorithm、mode、输出 checkpoint SHA、loaded input SHA、TF determinism 等，却没有检查 learning.contract == resolved routing.contract，更没有原 checkpoint contract 可交叉验证：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/receipt.py#L422-L523

复现条件

训练并保存一个 C3 DDQN checkpoint；把其 SHA 正确写入一个 C4 eval resolved config。由于 C3/C4 都是相同输入宽度、相同 Dense DDQN 架构，现有加载检查没有合同来源差异可拒绝。

影响

INFERENCE：正式实验可能声称“C4 eval”，实际执行的权重却是在 C3 状态语义下训练的。checkpoint 文件和 SHA 都是真的，所以这是比普通文件篡改更危险的语义身份假绿；模型比较、泛化结论和 contract attribution 均不可可靠解释。

F2 — TabularQ checkpoint 不校验 state-key 宽度；仓库现有测试已经把 4 维 key 当 C3 checkpoint 验证成功

严重度：major
状态：FACT；完整正式 receipt E2E 为 INFERENCE。

证据

C3 的真实 observation 宽度为：

7 (OWN)+4 (ORIGIN)+3 (DEST)=14

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L29-L52

但 Tabular loader 只校验每个 Q row 有 5 个 action value；它把 key_hex 直接 bytes.fromhex() 塞入 table，完全没有验证 key 的字节长度是否等于 8 * CONTRACT_DIMS[contract]，也没有在 table payload 内绑定 contract：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L600-L638

eval 未命中 table 时不会报错，而是返回全零行，并 deterministic 地选择第一个合法 action：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/learning.py#L640-L683

独立证据来自仓库自己的 migration test。测试 helper 明确构造的是 C3 learner：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/tests/test_qlearning_migration.py#L25-L43

但 test_save_load_roundtrip_verified 用 np.zeros(4)/np.ones(4) 训练 table，然后：

save_and_verify()

断言 checkpoint_verified is True

重新以 C3 eval 加载

断言 table 完整 roundtrip

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/CODE/leo_sim/tests/test_qlearning_migration.py#L128-L145

即当前测试实际上证明了：一个不满足 C3 observation contract 的 Q table 能被项目自己的 verification 认定为有效。

复现条件

给 C3 checkpoint 放入任意 4-double key（32 bytes），保持 row 为 5 个 Q 值并提供正确文件 SHA；加载可以成功。Kernel 真正产生的 C3 state 是 14-double（112 bytes），因此该 key 不可能命中。

影响

eval 会持续走 _row() 的“未见状态→全零行”路径，最终表现为 first-legal heuristic，而不是已训练 Q policy。

因此可能出现：

checkpoint SHA 正确 → checkpoint_verified=True → eval 有 decisions → 实际几乎/完全没有使用 checkpoint 中训练过的 Q 值。

这会直接污染学习臂有效性和 baseline 比较。

这与已知 H2-19 不重复：H2-19 已知的是“真正未见状态如何 tie-break”；F2 是 checkpoint 校验漏洞导致本该拒绝的模型被装载，从而人为制造所有状态未见。既有 H2-19 记录见：

github://fuguther/leo-direct-sim/blob/1599d3e3c7d5d74f22ddb497969f28fe8b90b73c/ANALYSIS/EXPERT-REVIEW-20260816.md#L143-L156
