D1 dynamic link rate post-fix 独立审阅

结论：REQUEST_CHANGES

对精确 commit 4f20cf2068008496d494794873fe70bd6ecc7c68 的只读 cold-start 审阅发现：active GSL 的 post-fix 确实把 geometry / GE / zero-rate 检查前移到了 dequeue 之前，但“unavailable GSL head is not dequeued”这一说法不能整体成立。至少存在一个可由代码直接证明的 retiring-uplink 绕过；此外，新的 pre-dequeue gate 使 GSL 的精确 recovery/deadline 竞速退化成 time_step 轮询，并造成 GE receipt counter 漏记。另有一个 ISL zero-rate/no-deadline 在 horizon 处形成零时间循环的 blocking 问题。

我未执行本地测试或 shell；以下为精确 commit 上的静态 RESULT_CANDIDATE。

Findings
F1 — BLOCKING — ISL zero-rate、无 deadline、无恢复时可在 horizon 形成 timeout(0) 无限循环

分类：FACT + INFERENCE

ISL 在 dequeue 前正确检查 zero MCS rate；当 rate 为 0 时，它寻找 next_rate 和 head packet expiry。如果二者都不存在，就等待到 horizon：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L565-L608

问题在于到达 env.now == horizon 后，同一分支再次执行：

Python
运行
yield k.env.timeout(max(0.0, k.horizon - k.env.now))

此时等价于 timeout(0)，随后 continue，队列仍非空、rate 仍为 0，于是继续在 horizon 调度零时长事件。与此同时 Kernel.run() 明确处理所有 t_next <= horizon 的事件，只有超过 max_events 才中断：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L2100-L2121

复现条件：

rate_model=mcs；

ISL geometry 本身 available；

mcs_rate_bps == 0 且直到 horizon 都不恢复；

data packet 无 deadline，或 control expiry 不在未来；

packet 位于 ISL queue。

当前测试几乎构造了这个条件：test_mcs_zero_rate_isl_head_stays_queued_until_recovery 放入一个 deadline=None 的 packet，ISL 永久 5900 km、rate=0，但只执行 6 次 env.step()，没有运行到 horizon，因此遗漏该故障：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/tests/test_link_budget_integration.py#L166-L190

影响： 正常的“零速率直到仿真结束”场景可能不是 natural_end，而是最终撞 max_events 成为 interrupted run。因此阻塞 D1 通过。

F2 — MAJOR — post-fix active GSL 虽然不再 dequeue unavailable head，但丢失了精确 recovery/deadline 调度

分类：FACT + INFERENCE

active uplink 的新 gate 确实有效：MCS 模式下，geometry unavailable、GE down、rate≤0 都在 _pick() 返回 packet 之前检查：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L273-L295

downlink _servable() 同样在 dequeue 前检查 geometry、GE 和 MCS rate：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L410-L429

因此，“active MCS GSL unavailable head remains queued”这一窄化后的 claim 是成立的。

但一旦 _pick/_servable 返回 None，两种 GSL server 都不再进入 _transmit()，而只是：

Python
运行
yield env.timeout(time_step) | wake

uplink：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L297-L306

downlink：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L431-L452

这使 _transmit() 已实现的精确 next_gsl_change、ge.next_up、next_slant_range_under、deadline/retirement race 在 active-GSL pre-service outage 上变得不可达：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L1205-L1296

而设计稿明确要求 zero-rate recovery 由 certified next_slant_range_under 唤醒，并和 deadline/retirement 竞速：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/ANALYSIS/LINK-BUDGET-DESIGN-20260816.md#L47-L65

复现条件：

active GSL；

当前 rate=0 或 GE/geometry down；

recovery 时刻 t_r 落在两个 endpoint/server tick 之间；

没有其他事件碰巧 poke server。

预期按设计应在 t_r 重新尝试；实际最早通常到下一 time_step polling point。短于一个 time_step、完全落在两次 polling 之间的 GE-up window 甚至可能完全错过。

同理，active GSL packet 留在普通 uplink/downlink queue 后，deadline 也由周期 sweep 而非 _transmit() 的 exact deadline event 处理，deadline fate 与 queue-area 结算存在最高约一个 tick 的延迟。

建议： 保留“不 dequeue”的修复，但 server idle wait 应直接 race 当前 blocked heads 的 deterministic recovery / GE-up / deadline / retirement，而不是统一 time_step polling。

F3 — MAJOR — retiring uplink 绕过 post-fix gate，unavailable GSL head 仍会被 dequeue 并占住共享 server

分类：FACT

UplinkServer._pick() 对 retiring link 使用了单独分支：

Python
运行
if link.state == "retiring":
    if p.assigned_sat == self.sat:
        return p

该 return 发生在 geometry / GE / MCS-rate 检查之前：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L273-L295

而 _run() 一旦获得这个 packet，马上从 endpoint queue 删除，减少 queued_bits 和 queue-area，并令它成为 current：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L307-L318

随后才进入 _transmit()，在那里发现 geometry / GE / rate down 并等待恢复或 retirement：

github://fuguther/leo-direct-sim/blob/4f20cf2068008496d494794873fe70bd6ecc7c68/CODE/leo_sim/kernel.py#L1205-L1296

复现条件：

两个 endpoint 共用同一 satellite uplink server；

endpoint A 的 link 已进入 retiring；

A 的 head packet 已 assigned_sat == sat；

A 的 GSL 此时 geometry down、GE down 或 MCS rate=0；

endpoint B active 且完全 servable；

DRR 先选择 A。

结果是 A 被 dequeue 后进入 pre-service waiting，整个共享 uplink 的 current 被 A 占据，B 无法被服务，直到 A recovery / deadline / hard retirement。

此外，A 在这段等待期间已经从 endpoint queue 移除，而 _transmit() 又特意不把 pre-service wait 算入 occupied，因此这段时间既不是 queue-area 又不是 link occupation，诊断记账出现空洞。

因此，本 commit 不能宣称一般性的“unavailable GSL head is not dequeued”。 downlink 的 retiring path 经过统一 _servable() gate，但 uplink 没有。
