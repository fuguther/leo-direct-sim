# Remote formal environment activation 独立审查报告

## 1. 变更定位与三条路径分别追踪

合同要求分别追踪 prepare、tmux child、fail 三条路径。当前文件中三处环境激活点：

- **tmux child**（`tmux_script`，`run-remote.sh:163-169`）：`cd` → `set -euo pipefail`（L165）→ `$REMOTE_ENV_ACTIVATE`（L166）→ `$q_python ... $q_runner_args`（L167）。此为既有路径。
- **prepare**（`remote_command`，`run-remote.sh:170-183`）：`set -euo pipefail`（L171）→ `cd`/`mkdir`/守卫（L172-175）→ **`$REMOTE_ENV_ACTIVATE`（L176，即本次新增的一行）** → prepare 调用（L177）。
- **fail**：L178-181 的 `if ! tmux new-session ...` 块内，`$q_python ... $q_fail_args || true`（L179）与 prepare 同属一个 shell，位于 L176 激活之后，因此自动继承已激活环境。

结论：三条路径现在都在 `$REMOTE_ENV_ACTIVATE` 之后解析 `$REMOTE_PYTHON`，环境一致性在构造上成立。

## 2. Shell 执行顺序与 heredoc 展开分析

- 两个 heredoc 均为**未加引号的 `<<EOF`**（L163、L170），因此 `$REMOTE_ENV_ACTIVATE`、`$q_python`、`$q_runner_args` 等在**本地构建期**展开为字面文本，再经 `printf '%q'` + `ssh ... "bash -lc ..."`（L184）整体送往远端。参数展开的结果在 bash 中不会被二次扫描展开，所以值中嵌入的字面 `$HOME` 等会留到**远端**执行时才展开——这对 `source "$HOME/..."` 类配置恰好是期望语义，但值得明确记录（见 F2）。
- `REMOTE_ENV_ACTIVATE` 由 `common.sh:33` 的 `: "${REMOTE_ENV_ACTIVATE:?...}"` 强制非空；`REMOTE_PYTHON` 缺省 `python3`（`common.sh:46`），经 `printf '%q'` 引用（`run-remote.sh:158`）。
- **激活失败语义**：远端在 `set -euo pipefail` 下执行，若激活命令失败（如 venv 路径不存在），shell 在 L176 处中止，prepare 不执行、tmux 不创建，非零退出码经 ssh 回传本地（L184）——fail-loud。代价是该次 launch 不会产生任何 nonce 状态回执（prepare 尚未运行），监控方按 nonce 查不到状态而非看到误导性 success，可接受，且与修复前 mkdir/pgrep/has-session 等 pre-prepare 失败的行为一致（见 F4）。
- **prepare 失败**：`prepare_launch` 自身写 failed 状态并 `return 2`（`remote_job.py:461-471`），远端 set -e 中止，tmux 不启动。闭环。
- **tmux 创建失败**：fail 动作在已激活环境中运行（L179），`fail_launch` 校验 nonce+session 匹配后才改状态（`remote_job.py:482-483`），`|| true` 保证 exit 2 不被掩盖。
- 一处既有的不对称（非本次引入）：`tmux_script` 里 `cd`（L164）在 `set -euo pipefail`（L165）**之前**，cd 失败不会立即中止（但后续相对路径会 fail-loud）；`remote_command` 顺序相反。仅记录，不要求改。

## 3. 授权、nonce、部署、fail-closed 是否被削弱

## 4. 回归测试对事故场景的针对性评估

事故场景：prepare 在**未激活**环境中用系统 python 运行，与 tmux child 环境不一致。

`test_remote_launcher_environment.py:15-23` 的做法：从源码中提取 `remote_command` heredoc 文本，断言字面量 `$REMOTE_ENV_ACTIVATE` 出现在 `$q_python ... $q_prepare_args` 之前。

- **能抓住什么**：修复前状态（remote_command 中无激活行）会使 `index()` 抛 ValueError → 测试红；激活被移到 prepare 之后 → 断言红。即它确实针对事故根因（prepare 缺激活），不只是无害字符串变化的摆设。
- **抓不住什么**（非阻断）：① 不覆盖 fail 路径顺序与 tmux child 的激活行（L166 若被删，无测试兜底）；② 纯源码文本顺序断言，不验证激活的语义效果（例如 remote.env 中 `REMOTE_ENV_ACTIVATE=true` 这种"非空但无效"的配置，common.sh 只查非空）；③ 若 heredoc 被改为 `<<'EOF'`（激活留到远端展开、远端无此变量而触发 set -u fail-loud），测试仍绿——但该情形恰好 fail-loud，可接受。
