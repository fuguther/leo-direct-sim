结论：REQUEST_CHANGES

结果类型：RESULT_CANDIDATE。

当前 commit 9ae6a71294419dc31cc6b24771aeeb91b14ed285 的 D1 主体方向基本成立：RF/MCS 公式与允许范围内的设计稿、golden 一致；ISL 零速率语义较完整；snapshot 已显式防止除零；receipt 的 rate_model / mcs_rate_samples 链路也已接通；真实发送开始后的 deadline / GE / geometry / retirement 竞速结构没有发现新的确定性错误。

但存在一个阻塞问题：active GSL（uplink/downlink）的零 MCS 速率在进入 _transmit 之前就被过滤，导致设计中声明的“认证恢复时刻 + deadline + retirement 精确竞速”实际上没有用于 GSL 零速率阶段，而是退化为 time_step 轮询。 这不只是精度问题；当 deadline 位于当前时刻和下一次 tick 之间，而 horizon 又早于该 tick 时，可以在自然结束时漏掉本应发生的 DATA_DEADLINE_EXPIRED。

F1 — blocking：GSL 零速率绕过精确 recovery/deadline race，可在 horizon 前漏 deadline fate

FACT

Uplink 的 _pick() 在 active link 上先计算当前 MCS；若 rate <= 0，直接返回 None，包继续留在 endpoint queue。若当前没有可服务项，MCS 模式只等待 time_step 或 wake：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L270-L325

Downlink 同样在 _servable() 阶段以当前 MCS=0 拒绝出队，并在没有可服务项时按 time_step 轮询：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L395-L455

这与 ISL 不同。ISL 在零速率时显式计算 next_isl_range_under()，并将 rate recovery 与 packet deadline / control TTL 放在同一个精确等待中，同时保持 head packet 在 queue：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L515-L650

而 _transmit() 本身已经实现了正确的 GSL 机制：rate<=0 时调用 rate_recover_fn，并精确竞争 recovery、expiry 和 retirement interrupt：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L1170-L1345

问题在于 active GSL 零速率时，上述 _transmit() 路径根本到不了。

队列 deadline sweep 也不是连续事件，而是由 endpoint/pending ticker 按 time_step 执行；并且 queued packet 使用 now > deadline：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L1365-L1450

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L1610-L1650

自然结束时 kernel 到 horizon 后直接进行 stop accounting 和 ledger.close_at_stop()：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L2075-L2145

而 kernel 顶层合同明确声明 horizon 时剩余 packet 结算为 IN_SYSTEM_AT_STOP：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/CODE/leo_sim/kernel.py#L1-L38

设计稿本身要求零速率使用认证 range-under recovery，并与 deadline / hard retirement 竞速，不是 tick polling：

github://fuguther/leo-direct-sim/blob/9ae6a71294419dc31cc6b24771aeeb91b14ed285/ANALYSIS/LINK-BUDGET-DESIGN-20260816.md#L45-L90

INFERENCE / reproduction condition

构造一个合法 MCS 配置，使某个已经 active 且 geometry-visible 的 GSL 当前 MCS rate 为 0；例如通过允许配置的 RF 参数降低可服务距离。令：

当前时刻 t=0

time_step_s=0.1

data deadline =0.05

horizon =0.075

在 (0, 0.075] 没有另一个能够 poke 该 GSL server 的事件

则 active uplink _pick() 会在 t=0 返回 None，其下一次 rate/deadline 检查预定在 t=0.1；endpoint deadline sweep 同样在 0.1，但 horizon 已于 0.075 到达。由 stop-close 语义推断，该 packet 会进入 horizon 剩余系统结算，而不是在 0.05 获得应有的 deadline fate。

即使 horizon 大于下一个 tick，不会产生错误终态，恢复和 deadline 仍会被量化延迟最多一个 time_step，与设计中的认证精确事件语义不符。

是否阻塞 D1 gate：是。

这是 supported configuration surface 上的 packet-fate / timing semantic error，而不是纯性能问题。

决定 constant mode 是严格“忽略 RF”，还是正式修改设计合同为“即使 constant 也验证 RF schema”。
