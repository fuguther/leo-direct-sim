F2 — 仍阻断：连续 rematch 可使两个 retired generations 同时使用同一 (sat,direction) transceiver

FACT + INFERENCE — severity: blocking

当前实现确实增加了 predecessor gate：一个非 retired的新 generation 在发现同一 (sat,dir) 的 retired predecessor 尚未 drain 时，会等待 predecessor 的 drained event。

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L651-L690

问题是这个 gate 被包在：

if not self.retired:

之下。

而每次 rematch 会把当时 current generation 标记为 retired=True，保留 control queue，并唤醒其 server：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L1120-L1133

Concrete reproduction condition

令同一 (sat,E) 依次出现 G0 → G1 → G2：

G0 已有长时间 in-service/control backlog。

第一次 rematch：G0 retired，G1 创建。

G1 收到 control packet；由于 G0 未 drain，G1 正确停在 predecessor gate。

在 G0 drain 之前发生第二次 rematch：G1 被置为 retired=True，G2 创建。

_poke(G1.wake) 使 G1 恢复执行。

G1 下一轮因为现在已经 retired，跳过 if not self.retired 的 predecessor gate，可开始 drain 自己的 control queue。

此时 G0 仍可处于 service/drain。

因此 G0 与 G1 可以并发占用同一个 (sat,E) 物理方向，违反任务明确要求的 exactly one transceiver per (sat,direction)。

当前 regression 只覆盖一次 old → new rematch，并仅检查 old control 最终送达；没有构造 G0 → G1 → G2，也没有断言两个 generations 的 service interval 不重叠：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/tests/test_dynamic_topology.py#L63-L80

F2 另一个 lifecycle 缺口：无 successor 时 drained generation 不会立即 reclaim

retired server 自己 drain 完时只触发 drained 并 return：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L651-L665

实际把 generation 从 _retired_isls 移到 accounting-only _retired_isls_done、并增加 _isl_dyn_drained 的动作只发生在 _purge_drained_retired()：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L1057-L1073

如果 rematch 直接删除该方向、没有 successor 等待它，则 drain 完成后没有必然调用 purge。更严重的是下一次 rematch 先进行 entity cap 检查，最后才 purge：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L1083-L1099

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L1134-L1138

复现：方向 E 被移除 → old E 稍后自然 drain → 无 successor 触发 purge → 下一周期 E 重新出现且 entity cap 恰好卡边界。已经 drain 的旧 generation 仍被 live 计数，可产生错误的 CapExceeded。

所以 round-1 F2 仍 OPEN，并且阻断 APPROVE。

F3 — entity cap 对 dynamic ISL 与 lazy endpoint 分别计数，组合后可超过 max_entities

FACT + INFERENCE — severity: major

初始化时两套基数都保存为初始 n_entities：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L899-L918

但 lazy endpoint 创建时仅检查：

∣endpoints∣+_entity_base

没有加入当前动态 ISL generation 增量：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L997-L1006

反过来，dynamic topology 创建新 ISL 时检查：

_n_entities_base+_isl_dyn_created−_isl_dyn_drained+planned_new

却没有加入已经 lazy-created 的 endpoints：

github://fuguther/leo-direct-sim/blob/4bfcf8040317d2bcaa8bb14201087fdbd5d269c5/CODE/leo_sim/kernel.py#L1093-L1099

Concrete reproduction condition

令初始计数为 B，配置 max_entities=B+1：

lazy activation 创建 1 个 endpoint：endpoint 检查允许，总数达到 B+1；

一个旧 ISL 尚在 drain 时 rematch 创建 1 个 replacement：dynamic 检查看不到该 endpoint，因此也允许；

两个检查各自均未超过 B+1，但组合 live entity 已达到至少 B+2。

因此 entity cap 目前并非全局 fail-closed。
