REQUEST_CHANGES — RESULT_CANDIDATE

Round-5 明确要求修复的两项，在静态代码层面均已按要求改动：

Finding 1 — major：正常 _decide() 的 zero-rate 路径仍绕过 certified wait，deadline/recovery 继续退化为 time_step polling
FACT

_decide() 在 destination 已有 active association、geometry up、但 downlink MCS rate 为 0 时，并没有把包送进 DownlinkServer；而是直接：

检查 MCS；

记录 attribution；

self.pending[sat].append(pkt)；

返回。

而函数入口的 deadline 判断仍是严格的 now > pkt.deadline，不是 >=。

证据：

github://fuguther/leo-direct-sim/blob/3acb6cea21247fd6af28f0c17af84eae53aea2c6/CODE/leo_sim/kernel.py#L2270-L2310

pending 本身没有 certified deadline/rate-recovery timer。常规重判来自 _pending_ticker()：

yield timeout(time_step)
_redecide_pending(...)

证据：

github://fuguther/leo-direct-sim/blob/3acb6cea21247fd6af28f0c17af84eae53aea2c6/CODE/leo_sim/kernel.py#L1680-L1692

ISL 的正常 decision path 有同样结构：zero-rate candidate 被判 unavailable 后也进入 pending，并没有进入 ISLLink 自己已有的精确 deadline/rate-recovery wait。

证据：

github://fuguther/leo-direct-sim/blob/3acb6cea21247fd6af28f0c17af84eae53aea2c6/CODE/leo_sim/kernel.py#L2345-L2405

INFERENCE / concrete reproduction

构造：

time_step_s = 0.7

destination association 一直 active；

geometry 一直 up；

downlink range 始终导致 MCS rate = 0；

无 handover / fresh association / 其他会调用 _redecide_cell_pending() 的事件；

t=0 调用 _decide()；

packet deadline = 0.5。

结果链：

t=0.0  _decide -> zero MCS -> pending
t=0.5  无 pending certified wake
t=0.7  _pending_ticker -> _decide
       now > 0.5 -> DATA_DEADLINE_EXPIRED

因此 fate 会在 0.7 而非 0.5 才产生。

更极端的是 deadline 恰好等于 tick，例如 deadline=0.7：由于 _decide() 使用 now > deadline，t=0.7 时不会 expire，而会再次进入 pending，下一次才可能在 1.4 expire。

同理，如果 downlink MCS 在 t=1.0 精确恢复而 tick 为 0.7，则正常 pending path 最迟可能到 t=1.4 才重新发现它，而刚修好的 DownlinkServer._gsl_wait_until() 完全没有机会介入。

为什么新 tail regression 没覆盖它

新的 regression 手动把 packet 放入 dl.queues，因此确实验证了 DownlinkServer 内部能够在 0.5 wake：

github://fuguther/leo-direct-sim/blob/3acb6cea21247fd6af28f0c17af84eae53aea2c6/CODE/leo_sim/tests/test_link_budget_integration.py#L680-L725

而现有正常 decision-level 测试明确验证 zero-rate downlink 被放入 pending：

github://fuguther/leo-direct-sim/blob/3acb6cea21247fd6af28f0c17af84eae53aea2c6/CODE/leo_sim/tests/test_link_budget_integration.py#L280-L318

因此两条路径是不同的；新 regression 没有覆盖生产正常 _decide → pending 路径。

风险： deadline 精确性和 certified MCS recovery 精确性依然依赖 packet 恰好已经进入 server queue；正常 zero-rate decision 不满足这一前提。

Finding 2 — major：GE 在 decision / ISL pre-gate 实际阻塞时，receipt 的 GE effectiveness 可能是假阴性
FACT

本轮 F4-DECIDE 修改确实读取了 GE 状态来避免误增 MCS counter：

if ge_up:
    mcs_zero_rate_holds += 1

    rate_blocked = True

证据：

ge_gsl_queries

ge_isl_queries

与此同时，receipt 将 effective.ge 完全由这两个 counter 重算：
