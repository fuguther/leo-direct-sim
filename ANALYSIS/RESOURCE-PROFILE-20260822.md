# VM 资源标定：24 vCPU / 64 GiB（2026-08-22）

## 目的与边界

本记录回答两个工程问题：一个 V2 仿真进程是否能通过增加 CPU 线程变快，以及多个独立实验并行时 CPU 和内存如何变化。运行均为**非正式资源诊断**，使用已部署主线的同一 20 s、140 星、M-Lab multi-OD + burst、MCS 配置；输出写入 VM `/tmp/leo-resource-profile-*`，不属于论文结果，也没有写入 `CODE/Results/`。

## 先确定真实 VM 配额

不能用宿主机的 `nproc` 和 `/proc/meminfo` 判断用户可用资源。宿主机可见的是 256 个逻辑 CPU、约 628 GB 内存；VM 的 cgroup v1 配额才是有效口径：

| 项目 | 观测值 | 解释 |
|---|---:|---|
| `cpu.cfs_quota_us` | 2,400,000 | 一个周期内最多 24 个 CPU 核的计算时间 |
| `cpu.cfs_period_us` | 100,000 | cgroup CPU 周期 |
| CPU 配额 | 24 vCPU | `2,400,000 / 100,000` |
| `memory.limit_in_bytes` | 68,719,476,736 bytes | 64 GiB |
| `cpuset.cpus` | `0-255` | 只是允许调度到宿主机哪些编号，不代表有 256 vCPU 配额 |

因此后续实验调度只能按 24 vCPU、64 GiB 设计，并保留系统和其它任务的安全余量。

## 观测结果

### 单个进程

单个非学习 V2 进程在不同时间点的 RSS：

| 运行时长 | CPU | RSS |
|---:|---:|---:|
| 约 14 s | 约 107% | 406 MB |
| 约 44 s | 约 101% | 456 MB |
| 约 83 s | 约 100% | 524 MB |
| 约 122 s | 约 100% | 608 MB |

这说明内存不是启动时固定不变的，会随事件/包处理过程中的 ledger、命运和中间对象增长；但本轮没有看到进程退出后匿名内存持续残留的证据。诊断进程结束后，cgroup 的匿名 RSS 回落到约 0.1 GB，剩余约 3--4 GB 主要是可回收文件缓存。

### 并行进程

按 `taskset` 将独立进程分别绑定到不同 CPU 核，得到以下工程诊断范围：

| 并行数 | 单进程 CPU | 典型单进程 RSS（中后段） | cgroup 现象 | 结论 |
|---:|---:|---:|---|---|
| 2 | 约 99% | 0.46--0.60 GB | 未见新增 CPU 节流 | 安全，但吞吐仍需重复测量 |
| 4 | 约 97--99% | 0.43--0.62 GB | 未见新增 CPU 节流 | 安全，可同时跑 4 个 |
| 8 | 约 99% | 0.43--0.62 GB | 未见新增 CPU 节流 | 安全，可同时跑 8 个 |
| 12 | 约 99% | 0.43--0.63 GB | 未见新增 CPU 节流；总内存约 7 GB 级别 | 当前非学习诊断的可用候选上限 |

单轮 wall-clock 诊断不是正式性能基准（VM 宿主负载、文件缓存和输出 I/O 会改变时间），所以不把这一轮的速度比写成论文结论。它能确认的是：单个进程约等于一个 CPU 核；并行 12 个仍远低于 64 GiB 内存上限，且没有触发 cgroup CPU throttle。

## 当前调度建议

1. **非学习仿真**：先用 `cpu_per_job=1`、`max_parallel_jobs=12`，每个进程显式绑定独立 CPU 核；不要给一个 SimPy 进程虚假的 8/16 线程。
2. **学习训练**：暂不套用 12 并发。先测 TensorFlow 线程池、单个模型 RSS、checkpoint 峰值和续训开销；第一版保守设为每任务 4 vCPU、并发 4--5，实测后再调高。
3. **内存 guard**：启动新任务前读取 cgroup `memory.current` 与 `memory.limit_in_bytes`，至少保留 25%（约 16 GiB）给系统、缓存和突发峰值；按实测峰值而非启动时 RSS 估算每个任务。
4. **分批并行**：正式实验仍要保留每个 run 的独立 session、launch nonce、CPU 绑定和回执；并行只改变调度，不改变 trace、seed、配置或分析配对。
5. **下一次标定**：对 8/12 并发各重复至少三次，记录精确 wall time、CPU time、峰值 RSS、cgroup throttle delta 和自然结束状态；只有吞吐稳定时才把 `max_parallel_jobs` 写入正式实验资源合同。

## 不应作出的结论

- 不能把宿主机 256 CPU / 628 GB 写成 VM 资源；
- 不能因为一次 12 并发没有 OOM，就宣称学习任务也能 12 并发；
- 不能把非正式诊断运行的 wall time 当成论文性能结果；
- 不能通过提高单个 SimPy 进程的 CPU affinity 数量，推断单个仿真会线性加速。
