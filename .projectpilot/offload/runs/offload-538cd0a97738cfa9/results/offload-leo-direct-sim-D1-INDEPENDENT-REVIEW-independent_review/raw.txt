2. 深挖：逐项证据、推理、复现与影响
2.1 F1 — major：MCS=0 的 pre-service wait 会让 Q0 snapshot 直接除零；非零但未开传时又会暴露陈旧的“服务速率”

FACT。 三个 server 在进入 _transmit() 前都会先计算一次 MCS rate，并直接写入 owner._service_rate_bps。因此 rate=0 时，该字段明确为 0.0，同时 _svc_phase 被设成 waiting_for_link。

Uplink 路径证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L291-L335

Downlink 路径同样如此：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L397-L455

ISL 路径也在 dequeue 后设置 _service_rate_bps / waiting_for_link：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L570-L620

而 snapshot_global() 的 _remaining_service() 会优先采用 _service_rate_bps；只要 phase 是 waiting_for_link，直接执行 bits / rate_bps，没有 rate_bps <= 0 guard：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L918-L980

FACT。 D1 自己已经构造了明确会进入这一状态的合法测试场景：ISL range 固定 5900 km 时，MCS=0，服务等待到 deadline，并断言 occupied 为 0。

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/tests/test_link_budget_integration.py#L131-L150

因此复现不需要假想异常输入。复现条件可写成：

YAML
links:
  rate_model: mcs
  max_isl_km: 6000

再使一个 Earth-clear ISL 在 packet 被选中时处于约 5900 km，并在 deadline 前不降到有效 MCS 距离。等待期间调用 kern.snapshot_global()。代码链是：

rate=0 → _service_rate_bps=0 → phase=waiting_for_link → _transmit() 等待 rate recovery → Q0 snapshot → _remaining_service() → bits / 0.0。

INFERENCE。 这会产生 Python ZeroDivisionError，从而使本来声明为 read-only 的 Q0 当前状态读取变成可崩溃接口。因为这一推论直接来自 Python 浮点除零语义和上述赋值路径，不依赖外部状态。

此外还有第二层问题。_transmit() 每轮先计算 geom_up/ge_up，但无论 geometry/GE 是否当前可用，都会先调用 rate_fn(t0)；只要 rate>0，就立即把这个 rate 写回 owner._service_rate_bps，之后才进入统一 availability gate：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L1160-L1225

这意味着如果当前 MCS rate>0、但 geometry 或 GE 是 down，snapshot 在 waiting_for_link 状态下会给出 bits / 当前旧采样rate；真正恢复并开始 transmitting 时 _transmit() 会再次采样，届时 MCS 档位可能已经变化。因此这个 remaining_service 并不是“当前正在进行服务的剩余时长”，也不是“未来真正开传时已知的服务时长”。

影响。 这是 D1 与既有 Q0 snapshot 合同的直接交叉回归。它不仅是显示值不漂亮：零速率情况会使 snapshot 不可调用；非零但 pre-service down-wait 情况则向 planner 提供一个尚未承诺、未来会重新采样的 rate。D1 设计稿明确要求“服务每次真正开始时才按当时斜距采样一次”，当前 snapshot 却把“等待期间的试探采样”包装成 service_rate_bps。

设计证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/ANALYSIS/LINK-BUDGET-DESIGN-20260816.md#L26-L32

严重度：major，建议合并前修。

最小修复方向不是简单把除零改成 inf。更一致的合同是：waiting_for_link 且动态 MCS 尚未真正开传时，service_rate_bps/remaining_service_s 应明确表示“未承诺”，例如 None；只有所有 geometry/GE/rate/retirement 条件均通过、真正进入 transmitting 的那个时刻，才把最终采样 rate 写入 owner。这样同时解决零除和 stale-rate 两个问题。

后果二：控制平面看到的拥塞也少一包

FACT。 control advertisement 的 ISL queue load 直接取：

link.data_bits + link.ctrl_bits

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L1520-L1535

而零速率 packet 在真正 transmit 之前已经从这两个数字里扣除。因此一个“物理上没发出任何 bit、正在等 MCS 恢复”的 packet 会从 advertised queue occupancy 消失。

INFERENCE。 这会低估拥塞，进而影响依赖控制缓存 queue information 的后续路由/学习决策。这里并非说 packet 丢失——fate ledger 仍能守恒——而是状态语义和拥塞积分不守真。

后果三：共享 GSL server 可以被一个 rate-dead endpoint 长时间占住

Uplink 是“一颗卫星一个共享 DRR server”，其 coroutine 在 yield k.env.process(k._transmit(...)) 返回之前不会再次进入 _drr_select()。Downlink 同样如此。

因此，如果某个 GSL endpoint 被选中后 MCS=0，当前实现不是“该 endpoint 留队并暂时不 eligible，让 DRR 看其他 endpoint”，而是整个共享 server 等这个 packet 恢复/deadline/retirement/horizon。

Downlink _servable() 只检查 association + gsl_available()，不检查 MCS，因此可以先把一个 geometry-visible 但 MCS=0 的 endpoint 选出来：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L397-L420

未验证。 默认 550 km / 25° 配置下是否实际存在 downlink slant 超过默认 20 GHz 最低 MCS 距离的常见时间窗，我没有在合同允许范围内运行轨道扫描，因此不把“默认场景必现 GSL HOL”写成事实。但配置允许更高 LEO altitude，且 downlink 的解析阈值明显低于 uplink；本地 Agent 应构造两个 endpoint 的确定性 geometry 单测验证这个共享-server效应。

影响。 F2 会改变 queue metric、控制观测以及在可触发 GSL zero-rate 时的共享资源公平性。这已经超出“只把固定 rate 替换成动态 rate”的 D1 目标，会引入新的调度语义。

严重度：major，建议合并前修。

更合理的实现方向是把 rate eligibility 放在“出队/claim packet”之前：零速率时 packet 保持 queue ownership，并单独安排 rate-recovery wake。尤其对共享 GSL，不能让一个当前 rate-dead flow 阻止 DRR 尝试其他 endpoint。ISL 因为同一 edge 上所有 packet 共享相同 MCS，允许整条 edge server sleep，但 queue bits/queue area 仍应保持 backlog，直到真正开始服务。

2.3 F3 — major：mcs_rate_samples 与 control_tx_started 都不是“真正 transmit start”的计数，导致 receipt 可以自洽地报告错误的 effective 语义

这一项结构上没有伪造漏洞，但语义上闭合到了错误事件。

FACT。 _transmit() 的顺序是：

计算 geometry up；

计算 GE up；

调用 rate_fn(t0)；

只要 rate>0，立即 mcs_rate_samples += 1；

然后才判断 geom_up and ge_up and rate_up；

三者都通过后，才把 phase 改成 transmitting。

证据：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L1160-L1275

因此存在两个方向的误分类。

false positive

如果 MCS rate>0，但当前 geometry 或 GE down，则 service 根本没有开始，却已经增加 mcs_rate_samples。之后 Kernel 定义：

effective["mcs"] = mcs_rate_samples > 0

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L2135-L2165

receipt verifier 又使用同一规则重算：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/receipt.py#L120-L156

于是一个没有发生任何真正 MCS-paced transmission、只是做过一次 positive rate probe 的 run，也可以被标成 effective.mcs=true。

false negative

反过来，如果 rate=0，MCS gate 已经实质性改变 packet 的时序/fate，但 counter 不增加。一个极端的 control-only、所有可选 ISL 都处于 5900 km zero-rate 的场景，MCS 机制真实地阻止所有服务，却可能得到 effective.mcs=false。

而 ISL control counter 更进一步：control_tx_started 在 packet dequeue 时就增加，发生在 MCS gate 之前：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/kernel.py#L570-L610

因此 zero-rate control packet 可以同时形成：

control.transmission_started > 0

_svc_phase == waiting_for_link

occupied ctrl_isl_s == 0

mcs_rate_samples == 0

effective.mcs == false

这几个字段单独都能通过类型/生命周期关系检查，却表达出相互矛盾的物理故事。

FACT。 receipt 的结构闭合本身是正确的。它把 rate_model 加入 REQUESTED_KEYS，把 mcs 加入 EFFECTIVE_KEYS，把 mcs_rate_samples 加入 MECHANISM_COUNTER_KEYS：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/receipt.py#L35-L78

mechanism counter key set 是 exact equality，不是宽松 contains：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/receipt.py#L650-L690

requested 又从 resolved config 重建，effective 从 ledger counters 重算：

github://fuguther/leo-direct-sim/blob/c0a1f182b3447d2c6f0a5d885ef07582e9f0dc42/CODE/leo_sim/receipt.py#L1032-L1064

所以这里不是 validator fail-open，而是 producer 与 validator 完全一致地采用了一个过早的“sample/start”定义。这类问题反而更容易逃过 receipt 验证。

影响。 D1 的核心是把实验差异归因到动态链路速率；如果 effective.mcs 可以 false-positive / false-negative，那么“某一臂是否真正受 D1 treatment 影响”这个证据字段失去精确含义。尤其用户要求的 mechanism 审计维度会因此不能仅靠 receipt 得出物理结论。

严重度：major。

建议将两个事件拆清楚：mcs_rate_queries 可以统计所有 probe；mcs_service_starts 只在所有 availability 条件通过且真实 transmitting 时增加，并用后者决定 effective.mcs。control_tx_started 同样应移动到真正开始 transmit 的时刻；若需要统计 dequeue/claim，应新增不同名字的 counter。

3. 对抗：主动攻击上述结论
3.1 对 F1 的反例攻击

替代解释： remaining_service_s 在 waiting_for_link 本来就只是“未来假设服务时长”，所以用预采样 rate 没问题；rate=0 可以理解成“无限服务时间”。

排除理由： 当前代码并没有返回 inf，而是执行真实的浮点除零；更重要的是 D1 明确选择“不用 dur=∞”，而改成 rate-down recovery gate。因此 snapshot 再把 zero-rate 映射成无限/除零与设计是相反的。且 _transmit 真正开传时会重新采样，所以等待期 positive rate 也不是已承诺的服务参数。

结论维持：major。

3.2 对 F2 的反例攻击

替代解释： packet 一旦被 server 领取，就已经不是 queue resident；即使尚未发 bit，把它从 queue_area 删除是正常 non-preemptive server reservation。

这个解释对传统“server busy but暂时链路down”的模型有一定合理性，而且既有 geometry/GE pre-service waiting 也使用了相似结构。

为何仍不足以排除 F2： D1 设计特地把 zero-rate 定义成“link down、排队等待恢复”，integration test 也称“service never started”；同时 control advertisement 使用 queue bits 表示真实 backlog。若 packet 连 transmit phase 都没有进入，却既不计 queue backlog，又不计 occupied，它落入了一个 accounting 真空。对共享 GSL 更严重：一个 rate-dead endpoint 能独占整个 DRR coroutine，这不是单纯 metric 定义问题。

结论维持：major。 但我把“默认 constellation 下一定会产生 GSL HOL”降为未验证，不作为确认事实；确认事实是 zero-rate pre-service packet 被提前出队及 queue accounting 消失。

3.3 对 F3 的反例攻击

替代解释： mcs_rate_samples 名字只是“曾经计算到一个有效 MCS rate”的 probe counter，而 effective.mcs 的含义也可以定义成“算法被调用过”，无需真实 service start。

排除理由： Kernel 自己对 effective 的注释是“really entered the send path”，D1 设计更明确说“服务每次真正开始时才按当时斜距采样”。如果一个 geometry-down packet 仅 probe 到正 rate 就使 effective=true，而一个 rate=0 gate 实质阻断整个 run 反而 effective=false，那么该字段不能稳定表示任一合理的“D1 treatment 实际生效”语义。control_tx_started 在 zero-rate 时提前增加进一步证明事件边界没有对齐。

结论维持：major。
