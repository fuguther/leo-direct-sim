ell，PL24 限定统计效力为 diagnostic。两个残留问题：

- **F10（minor, INFERENCE）**：coverage 与 demand 都把 1 度 cell 表示为其中心点（kernel.py:310 `gridmod.grid_center(cell)`；population.py:88-90 区域坐标即 grid center）。高纬度 1 度 cell 横跨约 55–111 km，"中心可见"不蕴含"整 cell 有接入机会"。由于 demand 源也在中心点，场景自洽，但 PL23 的 claim 边界应显式写明"populated-land 以 cell 中心点为代表"。最小修改：PL1 节加一句声明。
- 计划的 16,988 cell 数与 raster SHA（PL17）、三个外部文献链接（PL28-30）不在本审阅的授权读取/联网范围内，标 UNVERIFIED（见 open_items）。计划的 stop condition（PL106）会在执行时自行 fail-closed 校验 SHA，设计正确。

## 维度二：population+local-time Poisson 与 offered_mbps 语义

数学自洽：thinning 包络 `1+abs(amplitude)` 是 `max(0, 1+amp·cos)` 的合法上界，与现有 diurnal 路径（trace.py:610-615）一致；PL353 明确 offered_mbps 是调制前基线、realized_offered_mbps 是真相——短发射窗内 realized 会系统性偏离 target，但计划如实记录，可接受。嵌套族的包含概率用名义比值，母子 trace 共享同一调制，比值一致。一个缺陷：

- **F6（minor, FACT）**：计划新版 `_rate_multiplier` 把 `utc_start_hour` 加进 `uses_local_clock` 公共分支（PL336-342），该分支同时覆盖 legacy `mode: diurnal`；但 Task 1 校验（PL150-158）只限制 `temporal_model`，不限制 legacy diurnal 下 `utc_start_hour` 必须为 0。后果：合法配置 `mode: diurnal + utc_start_hour≠0` 会改变 trace 字节，而 manifest 的 `traffic_transform.diurnal` 仍是两键值（PL375；receipt.py:489-496 也只为 `mode=="diurnal"` 重建两键），变换记录不再完整描述实际变换（trace_identity 含完整 demand 组，config.py:802-813，字节级篡改仍会被 identity hash 抓住，所以是记录缺口而非验证漏洞）。最小修改：加一条校验——`utc_start_hour != 0` 仅允许 `population_gravity + local_diurnal_cosine`。

## 维度三：alias-rejection 精确性与接受率

精确性核验通过：提议 q(j) ∝ pop_j^γ，接受率 (floor/max(d,floor))^α ≤ 1，接受分布 ∝ pop_j^γ/max(d,floor)^α，与 scan 目标（trace.py:146-163）精确一致；抽到 src 即拒 = 条件化，无偏；cap 耗尽 raise TraceError（PL425-427）fail-loud，无静默回退。无灾难性接受率：在 profile 参数（α=1.25, floor=100km，PL660-661）下最不利的远洋岛屿源每抽接受率约 (100/3500)^1.25 ≈ 1.2%，期望约 84 抽，cap=10,000 的耗尽概率实际为零。残留：

- **F9（minor, INFERENCE）**：config 允许任意 α>0（config.py:546-547）；若未来取 α=5，远端源每抽接受率 ~3e-7，cap 必然耗尽——fail-loud 但编译不可用。计划的 benchmark 只测速度（PL435），不接受率分布。最小修改：sampler 在 companion 或 benchmark 产物中记录每源 min/mean 接受率，把"接近 cap"变成可观测信号。

## 维度四：nested master trace（严格子集 / RNG / 合同）

子集语义成立：master 用 demand 流生成、filter 流按候选逐包抽 uniform（PL457-461），`SeedSequence.spawn[i]` 的派生只依赖序号 i 与父种子（rng.py:26-29），demand 流不受新增 nested_filter 流影响，无串扰；各 child 用同一 master 与同一 filter 序列、不同阈值，天然严格嵌套；包 ID 重编号符合 PACKET_ID_CONTRACT；max_packets 施加于 master 候选数（PL461）正确。但有一个合同缺口：

- **F1（major, FACT）**：Task 6 的文件清单（PL446-451）不含 receipt.py，但嵌套编译实际消费 spawn[1]，而 manifest 的 `rng_streams` 被 receipt 硬校验为恰好 `stream_mapping(seed, ["demand"])`（receipt.py:312-315；trace.py:736 写入端同样硬编码）。两种写法都坏：记录双流 → `verify_receipt_dir` 必失败；只记 demand → 实际消费的流在 manifest 中不可见、验证器无法察觉，且 `nested-family.json` 完全在 receipt 验证的工件集之外。这违反仓库 fail-loud/记录完整的原则，且 receipt.py 属承重文件（AGENTS.md §20），其改动必须在计划中显式列出并接受独立复核。最小修改：Task 6 增加 `CODE/leo_sim/receipt.py` 到 Files，定义嵌套编译时 `rng_streams` 的合同（建议记双流并在 receipt 重建同样的分支），并把 nested-family.json 的核验责任写明（receipt 绑定 trace.csv 字节已覆盖 child 内容，family 链接关系由独立 verifier 负责——这一分工应在计划中显式化）。

## 维度五：coverage（footprint 公式 / 阈值 / 分块 / 可行性）

公式正确：球面同高度星座下 ψ_max = acos((R/r)·cos e) − e 是标准结果，`dot > cos(ψ_max)` 与 `ground_visible` 的严格 `>`（model.py:529-532）边界一致。算术核验通过：16,988 × 280 × 8,641 = 41,102,126,240，与 PL315 完全一致；8641 采样点（PL282）与 600s/60s → 11 采样（PL313）均正确。分块矩阵方案（端点分块 × 每时刻卫星向量）在 256 MiB 内可行，全量 24h/10s 估算为分钟级计算 + 约 2.4M 次 Python subpoint 调用，60 分钟门槛内可达。但：

- **F4（major, FACT）**：现有 fail-closed 护栏 `MAX_COVERAGE_CHECKS = 50_000_000`、`MAX_COVERAGE_ENDPOINTS = 10_000`（coverage.py:24-26）与计划直接冲突：计划自己的 smoke（PL306-313）就需要 16,988 端点（>10,000）和 16,988×11×280 = 52,323,040 次检查（>50M），全量审计 41.1B 更超出三个数量级。计划全文没有提到这两个上限，也没有说明新的 `scan_constellation_coverage` 路径如何重新派生护栏。按计划执行的第一次 smoke 会立即 fail-closed。最小修改：Task 3 中显式给出新路径的限额合同（端点上限 ≥ 16,988 的推导、按分块计数而非总比较数的检查上限），保持 fail-closed 语义而非静默放宽。

## 维度六：geometry_epoch_s 覆盖完整性

在授权读取范围内成立：kernel.py 无任何直接三角/自转计算，所有几何经 `self.geometry`（MemoizedGeometry 包装，kernel.py:1075），Constellation 构造点只有 kernel.py:1056-1061 与 coverage.py:187-191 两处，计划 Task 2 同时覆盖。`at = t + epoch` 同时平移轨道相位与地球自转项（model.py:497-508），`Constellation(epoch=x).ecef(s,t) == Constellation(epoch=0).ecef(s,t+x)` 精确成立；ecef 及全部上层方法归约到 subpoint（model.py:510-512），无遗漏路径。epoch 排除在 trace identity 外（PL176）正确（trace 字节不依赖几何），run 级 receipt 通过 config_sha256 绑定。**未决**：routing.py、learning.py、control.py 等不在本审阅授权读取范围内，不能排除其中存在直接用 t 的几何路径（见 open_items）。

## 维度七：scene classifier（access/route/ISL 区分能力）

- **F2（major, FACT）**：决策合同要求 `max_access_overflow_fraction` 与 `max_uplink_overflow_fraction` 分列（PL558-561），并要求"access、holding、uplink、ISL、downlink 的 wait/overflow 是独立字段"（PL608）。但 kernel 把下行队列溢出也记为 `ACCESS_QUEUE_OVERFLOW`（kernel.py:3317-3329，`dl.room(pkt.bits)` 失败分支），与接入侧溢出（kernel.py:2551）共用一个 fate。scene_check 只读、Task 7 文件清单（PL532-536）不含 kernel/fates，两个分列阈值无法从现有 fate 计算。最小修改：拆出独立 DOWNLINK 溢出 fate（kernel 承重改动，需独立复核），或把合同改为可从 ledger 连接推导的定义（如按包是否经过 satellite_ingress 分段）并在计划中写明。
- **F3（major, FACT+INFERENCE）**：route_clean 门有盲区。控制面开启时（profile PL686-689 enabled: true），`no_info` 不判 NO_ROUTE 而是进 holding 等待重决策（kernel.py:3362-3368），这些包最终沉淀为 IN_SYSTEM_AT_STOP（kernel.py:3600）；而计划明确"IN_SYSTEM_AT_STOP 是 fate，不是拥塞证据"（PL607），合同中没有任何门限制它的比例或 holding 滞留。后果：一个路由/信息受限的运行可以通过 route_clean，只要另有 ≥100 包进入 ISL（PL556），最终被判 NO_ISL_PRESSURE 甚至 ISL_PRESSURE_CANDIDATE——正是计划声称要消灭的误标（PL7、PL22）。最小修改：route_clean 增加 `max_in_system_at_stop_fraction` 或对 holding wait/overflow（HOLDING_QUEUE_OVERFLOW fate 已存在，kernel.py:1405）的门限。
- **F5（major, FACT 机制 + INFERENCE 量级）**：L4 利用率分子"served ISL bits"（PL597-601）不含控制流量：service_start/service_window 只为 DataPacket 记录（kernel.py:2431-2446 的 `isinstance(pkt, DataPacket)` 分支），而控制包与数据共享同一 ISL 队列容量且非抢占优先（kernel.py:743-747）。分母是几何可用容量采样（metrics.py:299-329 的 available 口径）。profile 用 vis_k=17、advertise 1s（PL688-689），在 280 星上近似全局泛洪，控制占用不可见地压低数据利用率、抬高数据排队时延。后果：真实高负载链路可能因分子漏记控制占用而低于 0.70 门限（漏判方向，尚且保守），但合同的"directed link utilization"语义与实际测量脱节，且 vis_k=17 无任何论证。最小修改：记录控制服务窗口或从 control ledger 计算控制占用并单列；或为 vis_k=17 给出测量依据并在报告中分列控制份额。
- **F7（minor, FACT）**：封闭状态表（PL72-83）中 GLOBAL_SUPPORT_DIAGNOSTIC、READY_FOR_ISL_PRESSURE_BRACKET、PRESSURE_NOT_FOUND_WITHIN_REGISTERED_ENVELOPE 在分类顺序伪码（PL578-593）中永不可达——L2 demand 层（PL66）没有对应分支。最小修改：补 L2 分支或显式说明这些状态由哪一步外部流程赋予。
- 可计算性其余部分核验通过：ISL link_id 是有向的 `isl:{sat}:{peer}`（kernel.py:1430-1436）；queue_enter 带 link_id（kernel.py:1425-1428），per-link per-window 队列时延可经 queue_id 与 service_start 连接推导；admission rate 有 metrics v2（metrics.py:389-390）；`require_isl_exposed_packets: 100`（PL556）虽未定义"exposed"的精确推导（建议定义为有任一 ISL queue_enter 或 service_window 的包），属 minor 定义缺口，并入 F7 档。
